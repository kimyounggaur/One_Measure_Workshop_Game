# 한 마디 조립실 음악이론 모바일 웹앱 개발 설계서

문서 버전: 1.0  
작성 기준일: 2026년 10월 19일  
문서 성격: 개발 착수용 제품·교육·상호작용·기술·콘텐츠·검증 명세  
대상 독자: 제품 책임자, 음악교육 검수자, 프런트엔드 개발자, 디자이너, QA 담당자

이 문서는 사용자가 음표와 쉼표 조각으로 한 마디를 조립하고, 결과를 듣고, 소리가 시작되는 순간을 직접 두드리는 모바일 우선 음악이론 웹앱을 구현하기 위한 설계서다. 첫 출시 범위는 4/4박자, 8분음표 단위 격자, 학습용 악기 한 종류, 퍼즐 6개와 자유 조립이다. 핵심은 “길이는 같아도 리듬은 달라질 수 있다”를 조작·청각·기호로 연결하는 것이다.

실제 앱을 제작하거나 배포한 결과가 아니다. 여기의 성능 수치, 학습 목표, 일정, 테스트 통과 기준은 개발 제안과 수용 기준이며 측정된 성과가 아니다. 일반 음악학습자를 대상으로 하되 나이·독해 수준·기기 분포는 아직 확정되지 않았다. 미성년자 전용 서비스, 교실 배포, 로그인·온라인 작품 공유는 별도 검토 후에만 추가한다.

## 1 읽는 순서와 핵심 결정

처음 읽는 개발자는 2~7장에서 제품과 음악 규칙을 이해하고, 8~12장의 화면·입력·판정을 구현한 다음 13~18장의 기술 계약을 따른다. 19~23장은 작업 순서와 출시 조건, 24~27장은 후속 확장과 실제 콘텐츠·검증 부록이다.

| 결정 | 첫 출시에서 확정할 내용 | 이유 |
| --- | --- | --- |
| 학습 단위 | 4/4 한 마디, 8개의 8분음표 칸 | 길이 합과 분할 관계를 눈으로 검증하기 쉽다 |
| 악기 | 직접 합성하는 부드러운 지속음 한 종류 | 긴 음과 짧은 음의 차이를 청각으로 드러낸다 |
| 편집 | 조각 선택 후 칸 탭을 기본, 드래그는 선택 | 작은 화면과 다양한 운동 능력을 함께 고려한다 |
| 채점 | 조립 이론 판정과 두드리기 타이밍 판정을 분리 | 기기 지연이나 손동작을 이론 오답으로 처리하지 않는다 |
| 저장 | 로그인 없는 기기 내 저장, JSON 내보내기와 가져오기 | 운영·개인정보·네트워크 의존을 줄인다 |
| 오디오 | Web Audio의 오디오 시계로 예약 | UI 프레임이나 일반 타이머를 음원 시계로 쓰지 않는다 |
| 콘텐츠 | 수작업 작성 퍼즐 6개, 버전이 있는 JSON | 문제·정답·설명·판정을 동일한 데이터로 검증한다 |
| 모바일 | 세로 화면 우선, 넓은 화면에서는 보조 정보 병렬 표시 | 한 손 조작과 읽기 흐름을 유지한다 |
| 확장 | 3/4와 6/8, 붙임줄, 점음표는 후속 | 첫 경험에서 박자·분할·연주 부담을 과도하게 늘리지 않는다 |

“가장 훌륭한 앱”은 검증되지 않은 최상급 표현으로 제품에 넣지 않는다. 이 설계에서 품질은 음악적으로 올바른 판정, 접근 가능한 조작, 중단에도 유지되는 작업, 설명 가능한 피드백, 게임 밖 과제로의 전이를 실제로 확인하는 절차로 정의한다.

## 2 참고자료를 제품 결정으로 바꾸기

사용자 제공 [음악 학습 앱과 음악 게임 5곳 비교](https://docs.google.com/document/d/1iXov6mc7A3DCGxOh8oCf5LAl468u_7R511OQxaH3lkk/edit)를 실제로 읽고 다음과 같이 사용했다. 그 문서의 작성 기준일은 2026년 10월 18일이며, 장단점을 직접 실험한 교육효과가 아닌 기능 분석으로 구분하고 있다. 이 구분을 본 설계에서도 유지한다.

- Rhythmic Village: 리듬 기호와 활동의 연결을 참고한다. 음표 캐릭터·명칭·화면·과제의 복제는 하지 않는다.
- Yousician·Simply Piano: 즉각적인 결과 설명, 단계별 학습, 느린 연습의 필요성을 참고한다. 첫 출시에는 마이크나 실제 악기 인식이 없다.
- DJMAX·beatmania IIDX: 재도전의 명료함과 입력 환경 설정을 참고한다. 정밀 타이밍 경쟁을 음악이론 이해의 지표로 사용하지 않는다.
- [Rytmos 제작사 소개](https://floppy.club/Rytmos): 퍼즐 해결 방식이 만들어지는 음악에 영향을 준다는 경험을 참고한다. 행성 퍼즐, 곡, 루프, 악기 녹음, 미술 자산, UI를 가져오지 않는다. 본 앱의 모든 문제·소리·그림은 새로 만든다.

제품의 고유 경험은 한 마디의 시간 예산을 사용자가 직접 설계하고, 길이·시작 횟수·침묵 구간의 차이를 즉시 비교하는 것이다. “퍼즐을 풀면 음악이 나온다”에서 한 단계 더 나아가, 왜 달라졌는지 학습자가 설명하도록 한다. 이것은 제품 가설이며, 다른 제품보다 교육효과가 높다는 근거는 아직 없다.

## 3 사용자와 이용 상황

### 3.1 현재의 가정

주요 사용자는 음표 길이와 쉼표를 처음 배우거나 다시 익히는 일반 음악학습자다. 첫 사용 전에 악기를 소유하거나 오선보를 읽을 필요는 없다. 한 번에 약 5~10분 동안 1~3개 문제를 풀 수 있는 짧은 사용을 가정한다. 이 시간은 설계 목표이지 관찰값이 아니다.

교사 없이 혼자 접근할 수 있게 하되, 교사가 화면을 보여 주며 “같은 길이인가?”, “소리가 몇 번 시작했는가?”를 질문하는 상황도 지원한다. 교사용 계정·과제 배포·학생 기록 수집은 MVP에 포함하지 않는다.

연령이 정해지지 않았으므로 유아용 말투, 읽기 능력, 법정 동의 절차를 임의로 가정하지 않는다. 첫 파일럿에서 성인 입문자와 음악교사를 우선 모집하는 방안을 제안한다. 아동 파일럿을 추진하면 보호자 동의·아동의 참여 의사·수집 최소화·관할 규정 검토가 먼저 필요하다.

### 3.2 해결하려는 구체적인 혼동

1. 음표가 네 개 있어야 4/4 한 마디라고 생각한다.
2. 쉼표는 시간을 차지하지 않는 빈칸이라고 생각한다.
3. 2분음표 한 개와 4분음표 두 개가 길이도 같고 소리도 같다고 생각한다.
4. 소리가 시작하지 않는 칸을 전부 쉼표로 해석한다. 실제로는 긴 음이 이어지는 칸일 수 있다.
5. 8분음표를 넣으면 곡의 BPM이 빨라진다고 생각한다.
6. 박자표의 분모가 언제나 실제로 세는 큰 박을 뜻한다고 일반화한다.
7. 게임의 탭 점수가 낮으면 음표 길이를 이해하지 못했다고 생각한다.

각 혼동은 별도 오류 코드·피드백·평가 문항으로 연결한다. 모든 오류를 “다시 해 보세요”로 처리하지 않는다.

## 4 교육 목표와 평가 설계

### 4.1 목표와 관찰 가능한 행동

| 목표 ID | 학습자가 할 수 있어야 하는 행동 | 앱 안의 증거 | 게임 밖 전이 확인 |
| --- | --- | --- | --- |
| LO1 | 4/4 한 마디의 총 길이를 4분음표 4개 분량으로 설명한다 | L1·L4의 완성도와 길이 설명 | 색 없이 주어진 음가의 합 판단 |
| LO2 | 4분음표 1개와 8분음표 2개의 총 길이가 같음을 보인다 | L2의 분할, 남는 칸 0 | 새 기호 순서에서 동치 길이 선택 |
| LO3 | 쉼표가 정해진 길이의 침묵임을 표현한다 | L3·L5의 명시적 쉼표 배치 | 악보에서 소리 없는 구간 표시 |
| LO4 | 총 길이, 발음 횟수, 음의 지속 길이를 구분한다 | L4·L6 비교 질문 | 같은 onset·다른 duration의 사례 분류 |
| LO5 | 조건에 맞는 여러 리듬을 만들고 차이를 설명한다 | L4의 3개 해답, L5의 2개 해답 | 처음 보는 조건으로 한 마디 작성 |
| LO6 | 일정한 큰 박 안에서 8분 분할을 듣고 읽는다 | L6 모델 듣기와 조립 | 색·격자 없는 리듬을 읽거나 따라 하기 |

### 4.2 이론 이해와 운동 수행의 분리

이론은 작성된 이벤트와 문제 조건으로 판정한다. 탭 정확도, 반응속도, 음량, 특정 기기 사용 여부는 이론 통과 조건이 아니다. 직접 치기는 소리가 시작되는 시점의 연습이며 음을 얼마나 오래 누르는지 평가하지 않는다. 화면에 “시작 박자 연습: 길게 누를 필요 없어요”라고 표시한다.

긴 음의 길이는 조립과 듣기·비교 문항으로 학습한다. 길이 수행 평가를 나중에 추가하려면 press/release를 별도로 측정하는 모드와 접근성 대안을 마련해야 한다. MVP의 탭 데이터를 음가 지속 수행 능력으로 해석하지 않는다.

### 4.3 짧은 사전 진단과 사후 확인

첫 방문에 진단을 강제하지 않는다. “지금 시작”과 “내가 아는 것 확인하기”를 제공한다. 진단은 T1~T4 네 문항, 시간 제한 없음, 개별 정답을 보기 전까지 힌트 없음으로 한다. 거절하거나 중간에 나가도 콘텐츠 접근을 막지 않는다.

사후 확인에는 같은 원리를 다른 순서·다른 그림으로 묻는 T5~T8을 사용한다. 사전·사후에 동일한 정답 위치를 반복하지 않는다. 결과는 원점수와 문항별 변화로 보여 주고 “이 앱 때문에 향상됐다”라고 결론내리지 않는다. 학습효과 검증에는 비교조건, 표본 설계, 결측·연습효과 통제와 별도 연구 검토가 필요하다.

7일 뒤 재확인은 앱을 다시 방문했을 때 선택할 수 있는 카드로 제안한다. 알림·푸시·이메일 발송은 MVP에 없다. 미방문을 실패나 망각으로 해석하지 않는다.

### 4.4 학습 성공의 제품 검증 기준

개발 수용 기준과 교육효과 가설을 구분한다.

- 개발 수용: 모든 정답 fixture가 통과하고, 대표 오답이 정확한 이유로 실패한다. 이는 자동 검사할 수 있다.
- 사용성 가설: 도움 없이 첫 조각을 놓고 쉼표로 빈칸을 채울 수 있다. 최소 5명 규모 탐색적 사용성 관찰은 문제 탐지용이며 효과 검증이 아니다.
- 학습 가설: 색·격자가 없는 새 문제에서도 음가와 쉼표를 구분한다. 실제 전이 평가를 수행하기 전까지 효과를 주장하지 않는다.
- 접근성 수용: 드래그 없이 모든 조립, 키보드만으로 학습 완료, 오디오 없는 경로에서 이론 완료가 가능하다. 청각 없이 청음 능력이 측정됐다고 표시하지 않는다.

## 5 범위와 우선순위

### 5.1 MVP에 반드시 포함

- 한국어 UI, 세로 모바일·태블릿·데스크톱 반응형 레이아웃
- 4/4, 8분음표 격자 8칸, 한 성부·한 마디
- 온음표·2분음표·4분음표·8분음표와 대응 쉼표를 자유 모드 팔레트에 제공
- 퍼즐마다 제한된 팔레트·잠긴 조각·조건 설명
- 6개 퍼즐, 튜토리얼, 자유 조립, A/B 비교, 되돌리기·다시 실행
- 모델 듣기·내 조립 듣기·정지·메트로놈·템포 변경
- 선택적 탭 연습, 시작 전 한 마디 카운트인, 보정·평가 신뢰도 안내
- 이론·탭 결과 분리, 다중 정답, 개념별 힌트 3단계
- 로컬 자동 저장·복구, 데이터 내보내기·검증 후 가져오기
- 첫 온라인 로드 완료 후 핵심 기능 오프라인 사용
- 키보드·스크린리더·큰 글자·동작 줄이기·드래그 대체 조작
- 오류 및 버전 표시, 자동화된 도메인·상태·UI·오디오 회귀 테스트

### 5.2 MVP에서 제외

마이크·MIDI·실제 악기 자동 인식, 로그인·클라우드 동기화, 랭킹·멀티플레이, 광고·결제·구독, UGC 공개 갤러리, 기존 게임 곡, 생성형 AI의 실시간 정답 판정, 16분음표·셋잇단음표·스윙·변박·다성부·한 마디를 넘는 붙임줄 편집을 제외한다.

모바일 앱스토어 패키징이나 특정 서비스로의 배포도 이 문서 작성 작업에 포함되지 않는다. 실제 개발을 시작할 때 저장소·호스팅·도메인·예산을 별도로 정한다.

### 5.3 출시 후 순서

1. 첫 출시의 음악·접근성·저장·오디오 품질 안정화
2. 3/4와 6/8의 묶음 비교, 점4분음표, 기본 강세
3. 붙임줄 편집과 길이 유지 과제, 16분 분할
4. 두 마디 프레이즈·질문과 응답·다른 악기 음색
5. 검증된 필요가 있을 때만 교사용 기능·데이터 동기화

확장 기능이 MVP의 저장 형식이나 의미 모델을 뒤집지 않도록 시간 단위와 박자 모델은 처음부터 일반화한다. 화면과 콘텐츠는 첫 범위에 맞게 제한한다.

## 6 음악 규칙과 용어 계약

### 6.1 시간 단위

음표의 이름은 온음표에 대한 비율을 뜻한다. 이 앱의 4/4에서 4분음표가 한 박이고 8분음표는 반 박이다. “4분음표는 언제나 한 박”이라는 문장은 사용하지 않는다. 박자표의 분모를 모든 박자에서 큰 박의 단위라고 일반화하지 않는다. 단순박자와 복합박자의 일반적인 구분은 [Open Music Theory의 박자 설명](https://openmusictheory.github.io/meter.html)을 참고한다.

개발용 설명에서는 `u`를 8분음표 1개 길이로 사용한다. `u`는 초도 아니고 모든 박자의 한 박도 아니다. UI에서는 “반 박”, “8분음표 1개 길이”로 보여 주고 내부 단위 `u`는 노출하지 않는다.

| 조각 | 온음표 대비 길이 | 4/4의 박 수 | u | 내부 tick |
| --- | --- | --- | --- | --- |
| 온음표·온쉼표 | 1 | 4 | 8 | 1920 |
| 2분음표·2분쉼표 | 1/2 | 2 | 4 | 960 |
| 4분음표·4분쉼표 | 1/4 | 1 | 2 | 480 |
| 8분음표·8분쉼표 | 1/8 | 1/2 | 1 | 240 |

`PPQ = 480`으로 고정한다. 즉 4분음표 1개가 480tick이다. 4/4 마디 길이는 `4 × 4/4 × 480 = 1920tick`이다. 표기 분수는 기약분수의 정수 분자·분모로 저장하고, 음가 합·겹침·정답 판정에서는 부동소수점 초를 사용하지 않는다.

후속 `3/4`는 1440tick, `6/8`도 1440tick이다. 길이가 같더라도 묶음과 강세가 달라 같은 박자라고 판단하지 않는다. 셋잇단음표 확장 시 8분 셋잇단음표는 160tick으로 정확히 표현할 수 있다. 지원하지 않는 분모는 반올림하지 말고 명시적으로 거부한다. 예를 들어 온음표의 1/7은 이 PPQ에서 정수 tick으로 정확히 표현되지 않으므로 후속 설계 변경 전까지 입력을 받지 않는다.

### 6.2 세 가지 정보를 분리

- **onset**: 음이 새로 시작하는 순간. 음표의 왼쪽 경계다.
- **duration**: 이벤트가 차지하는 음악적 시간 길이. 음표와 쉼표 모두 가진다.
- **silence**: 명시적인 쉼표 구간. 빈 편집 칸과 다르다.

`N4`는 한 번 시작하여 4u 동안 지속되는 음이다. `N2 N2`는 같은 총 4u지만 두 번 시작한다. `N1 R1`과 `N2`는 모두 2u이고 onset은 시작점 하나로 같지만, 앞의 것은 후반 1u가 침묵이므로 리듬의 지속·쉼 구조가 다르다. 정답 비교를 onset 배열만으로 구현하면 이 차이를 놓친다.

MVP에서 하나의 음은 모든 음고가 동일하다. 내부 pitch는 MIDI 60에 대응하는 주파수를 쓰되 학습자에게 음높이를 시험하지 않는다. 반주가 없으므로 소리 없는 쉼 구간이 명확히 들려야 한다.

### 6.3 빈칸과 쉼표

조립 중 미배치 칸은 `unknown`이다. 자동으로 쉼표를 저장하지 않는다. 미리 듣기에서는 빈 구간이 물리적으로 무음이 되지만 “빈칸은 아직 결정하지 않은 시간이에요”를 보여 준다. 한 마디가 다 채워지지 않으면 주문 제출은 통과하지 않는다.

“남은 칸을 쉼표로 채우기”는 자유 모드에서만 명시적인 편집 명령으로 제공한다. 각 빈 구간의 왼쪽부터 남은 길이 이하인 가장 큰 지원 쉼표(8/4/2/1u)를 반복 선택하여 채운다. 퍼즐에서는 팔레트·재고 조건을 우회하지 않도록 이 명령을 숨긴다. 적용 전에 바뀔 구간을 표시하고 사용자가 실행하면 실제 쉼표 이벤트를 만든다. 한번의 undo로 되돌릴 수 있다. 쉼표는 삭제나 투명한 배경으로 표현하지 않는다.

온쉼표 기호는 통상 문맥에 따라 한 마디 전체의 쉼을 나타낼 수도 있다. MVP는 4/4이므로 고정 1920tick과 일치한다. 후속 박자에서는 `whole-value rest`와 `measure rest`를 다른 데이터 의미로 다룬다. 3/4에서 온쉼표 모양의 마디쉼표를 4박으로 계산하면 안 된다.

### 6.4 붙임줄과 음표 분할

붙임줄은 같은 음높이의 인접한 음을 연결하여 한번 시작한 소리를 지속시킨다. 따라서 4분음표 두 개의 붙임줄은 총 2박·발음 1회이며, 붙임줄 없는 두 음은 총 2박·발음 2회다. 쉼표 사이에는 붙임줄을 적용하지 않는다. [musictheory.net의 점음표와 붙임줄](https://www.musictheory.net/lessons/14)을 개념 검수 출처로 사용한다.

MVP에서 사용자가 붙임줄을 직접 그리는 기능은 없다. 자동으로 음표를 둘로 나누면 새로운 발음이 생기는 `splitAndRearticulate` 작업으로 정의한다. 긴 음을 그리기 편하게 조각내는 표기용 분할은 별도 `notationFragments`로 관리하고 오디오 onset을 늘리지 않는다. 이 둘을 같은 “나누기” 함수로 구현하지 않는다.

### 6.5 표기 규칙

상단에는 박 번호 `1 · 2 · 3 · 4`, 하위에는 `1 & 2 & 3 & 4 &`를 표시한다. 한 박 안의 8분음표 두 개는 보조 악보 보기에서 빔으로 연결할 수 있다. 빔은 발음이나 길이를 바꾸지 않는다. 쉼표는 표준 기호와 텍스트 이름을 함께 제공한다.

첫 출시의 시간 막대는 정확한 음가와 시작 위치를 우선한다. 보조 한 줄 리듬 악보는 같은 데이터의 파생 표현이다. 막대를 음표 아이콘 개수만큼 균등 배치하면 안 된다. 절반 길이 조각은 실제로 절반 너비를 차지한다. 2분음표가 두 번째 박에서 시작하는 것처럼 읽기 관습상 더 명료하게 표기할 수 있는 사례는 틀린 음악으로 거부하지 않는다. 보다 정교한 붙임줄 기반 재기보는 후속 렌더러에서 처리한다.

## 7 핵심 플레이 흐름

### 7.1 한 문제의 순서

1. 주문 읽기: 목표, 사용할 조각, 고정된 조각 확인
2. 예측: “완성하면 소리는 몇 번 시작할까요?” 같은 선택형 질문. 해당 문제에만 사용
3. 조립: 조각 선택 → 빈 시작 칸 선택 → 배치
4. 듣기: 한 마디 카운트인 후 결과 재생. 원하면 모델과 A/B 비교
5. 확인: 길이·쉼표·문제 조건을 분리해 검사
6. 설명: 달라진 점을 선택하거나 짧은 확인 질문에 답함
7. 직접 치기: 선택 사항. 정답으로 만든 리듬의 시작 시점을 따라 탭
8. 다음 문제 또는 다른 정답 만들기

주문은 제한시간이 없다. 탭 연습의 속도도 이론 문제의 난이도에 자동 합산하지 않는다. 실패 시 목숨·하트·재화·광고 시청을 요구하지 않는다.

### 7.2 게임의 보상

한 문제 통과 때 “이번에 찾은 관계” 한 줄과 조립품 도장을 얻는다. 예: “4분음표 하나를 8분음표 둘로 바꿔도 총 길이는 같아요.” 도장은 성적 순위가 아니라 학습 기록이다. 첫 시도 성공에만 특별 보상을 주어 탐색을 불리하게 만들지 않는다.

자유 모드에서는 자신의 한 마디를 이름 없이 “내 리듬 1”로 저장하고 두 버전을 비교한다. 제목 입력은 선택이며 로컬 전용이다. 완성 리듬의 총 길이·발음 횟수·쉼 길이를 함께 보여 준다. 전부 쉼표인 작품도 완성된 마디로 인정하되 탭 점수는 산출하지 않는다.

### 7.3 힌트 사다리

- 힌트 1: 개념을 말한다. “쉼표도 시간을 차지해요.”
- 힌트 2: 관련 구간을 표시한다. “세 번째 박의 두 칸을 살펴보세요.”
- 힌트 3: 한 단계만 시연한다. “이 조각을 4분쉼표로 바꾸면 어떻게 들릴까요?”

마지막에 “해답 보기”를 선택하면 답을 적용하고 이유를 설명한다. 기록에는 `assisted`를 남기되 진행을 막지 않는다. 힌트를 열기 전에 무조건 여러 번 틀리도록 강요하지 않는다. 같은 실패가 세 번 이어지면 더 긴 설명 대신 첫 개념 시연으로 돌아가는 버튼을 제안한다.

## 8 첫 사용 튜토리얼

튜토리얼은 약 2분을 목표로 하되 제한시간과 자동 넘김을 사용하지 않는다. 모든 단계에 “나중에 보기”와 재실행 경로가 있다.

### TUT1 소리와 화면 켜기

화면: “한 마디를 함께 만들어 볼까요?” / “소리 켜고 시작” / “소리 없이 시작”. 소리 켜기 동작 안에서 AudioContext를 생성 또는 resume한다. 시스템 음량을 임의로 바꾸지 않는다. 재생이 허용되지 않으면 설정 설명과 재시도 버튼을 보여 주고 조립은 계속 가능하다.

### TUT2 한 박을 놓기

4분음표 조각만 보여 준다. 조각의 표기는 “4분음표 · 1박 · 2칸”. 선택 후 첫 칸을 탭하면 처음 두 칸이 하나의 막대로 채워진다. 안내: “음표 한 개가 두 칸을 차지해요.” 다른 칸을 눌러도 오류음은 내지 않고 가능한 시작 위치를 표시한다.

### TUT3 나누어 듣기

4분음표 하나를 듣고, “둘로 나누어 다시 치기”를 누르면 8분음표 두 개가 된다. 비교 결과: 총 길이 1박 유지, 시작 1회 → 2회. 원래와 바꾼 리듬을 각각 한번 듣는다. 자동 재생은 사용자가 처음 허용한 세션에서도 반드시 화면의 재생 의도를 따라 수행한다.

### TUT4 쉬는 시간

4분음표를 4분쉼표로 바꾼다. 시간 막대의 길이는 유지하고 음소거 표시와 쉼표 기호가 나타난다. “쉼표는 정해진 시간 동안 쉬는 조각이에요.” 빈칸으로 삭제한 상태를 나란히 보여 주어 완료 상태가 다름을 설명한다.

### TUT5 직접 치기

완성된 `N2 N2 R2 N2`를 한번 듣는다. “소리가 새로 시작할 때만 아래 패드를 눌러 보세요.” 4박 카운트인 후 연습하며, 실패 판정 없이 세 번의 목표 순간을 보여 준다. 이 단계의 성적은 저장하지 않는다. “건너뛰고 조립 계속”을 항상 제공한다.

## 9 첫 퍼즐 6개 상세 명세

이 장의 기호 `N`은 소리, `R`은 쉼, 뒤 숫자는 u 단위 길이다. `N2 N2 R2 N2`는 4분음표·4분음표·4분쉼표·4분음표다. 배열은 왼쪽에서 오른쪽으로 빈틈없이 이어진다. onset 숫자는 0부터 시작하는 u 위치다. 실제 사용자 화면에는 이 개발 기호를 그대로 쓰지 않는다.

공통 템포 설정은 L1~L5에서 4분음표=72 BPM, 범위50~120 BPM이다. L6는 60 BPM, 범위50~100 BPM이다. 모두 카운트인은 4분음표 4박이다. 각 문제의 예시·정답은 템포와 무관하다.

### L1 네 박의 선반

- 목표: LO1. 한 마디의 총 길이를 처음 확인한다.
- 주문: “4분음표 네 개로 한 마디를 채워 주세요.”
- 시작: 빈 8칸. 팔레트: N2만. 무제한 재료이지만 주문은 정확히 4개.
- 기본 템포: 4분음표 = 72 BPM. 허용 연습 범위: 50~120.
- 정답: `N2 N2 N2 N2`. onset `[0,2,4,6]`, 소리 길이 8u, 쉼 0u, 발음 4회.
- 통과 조건: 빈칸 0, 겹침 0, 총 8u, 이벤트 네 개가 모두 N2.
- 오답 A: `N2 N2 N2` → 6u만 배치. “한 박, 두 칸이 남았어요.”
- 오답 B: 마지막에 N2를 마디 끝 밖에 배치 → 편집 단계 거부. “조각이 한 마디 밖으로 나가요. 시작 칸을 앞쪽으로 옮겨 주세요.”
- 확인 질문: “마디를 채운 총 길이는?” 선택 2박/4박/8박. 정답 4박. 8칸과 8박을 혼동하면 두 칸이 한 박임을 강조한다.
- 힌트 1: 박 번호마다 4분음표가 놓인다. 힌트 2: 첫 빈 박 표시. 힌트 3: 하나 배치.
- 직접 치기: 4회. 낮은 점수로 퍼즐 통과를 취소하지 않는다.

### L2 한 박을 둘로

- 목표: LO2·LO4. 길이를 유지하면서 발음 횟수를 늘린다.
- 주문: “두 번째 박의 4분음표를 8분음표 두 개로 바꿔 주세요.”
- 시작: `N2 N2 N2 N2`. 첫·셋째·넷째 박은 잠금. 편집 가능 구간 `[2,4)`u.
- 팔레트: N1. “나누기” 동작은 이 문제에서 시연 후 사용 가능.
- 정답: `N2 N1 N1 N2 N2`. onset `[0,2,3,4,6]`, 길이 8u, 발음 5회.
- 통과 조건: 잠금 영역 원본 유지, 편집 구간을 N1 두 개로 채움, 빈칸 없음.
- 오답 A: N1 하나만 배치 → “반 박이 남았어요. 8분음표 하나의 길이는 반 박이에요.”
- 오답 B: N2를 그대로 제출 → “길이는 맞아요. 이번 주문은 그 한 박을 두 번 시작하는 소리로 바꾸는 거예요.”
- 확인 질문: “바꾼 뒤에도 같은 것은?” 총 길이/발음 횟수. 정답 총 길이.
- A/B: 원래 4회와 새 5회. 같은 BPM, 같은 시작·끝에 재생한다.
- 직접 치기: 목표 5회. 두 번째 박만 느리게 반복하는 연습 제공.

### L3 세 번째 박의 쉼

- 목표: LO3. 침묵도 마디의 일부임을 이해한다.
- 주문: “세 번째 박은 쉬고, 나머지 박은 4분음표로 채워 주세요.”
- 시작: 빈 8칸. 팔레트: N2·R2.
- 정답: `N2 N2 R2 N2`. onset `[0,2,6]`, 소리 6u, 쉼 2u, 발음 3회.
- 통과 조건: 네 박의 종류가 note/note/rest/note, 각 길이 2u.
- 오답 A: 세 번째 박을 비워 둠 → “여기는 아직 빈칸이에요. 쉬겠다는 뜻을 쉼표로 표시해 주세요.”
- 오답 B: `N2 R2 N2 N2` → “쉬는 길이는 맞아요. 이번에는 세 번째 박에서 쉬어야 해요.”
- 확인 질문: “쉼표를 넣으면 한 마디의 길이가 줄어드나요?” 정답 아니요.
- 직접 치기: 3회. 셋째 박에 누르면 “쉬는 구간에서 한 번 눌렀어요”로 설명한다.

### L4 같은 길이 적은 시작

- 목표: LO1·LO4·LO5. 지속음과 재발음을 구분하며 여러 답을 찾는다.
- 주문: “2분음표 한 개와 4분음표 두 개로 한 마디를 만들어요. 세 번 시작하는 소리면 순서는 자유예요.”
- 시작: A에 `N2 N2 N2 N2` 비교용, B는 빈칸. 편집 대상은 B뿐이다.
- 팔레트 및 재고: N4 한 개, N2 두 개. 쉼표 없음.
- 정답 1: `N4 N2 N2`, onset `[0,4,6]`.
- 정답 2: `N2 N4 N2`, onset `[0,2,6]`.
- 정답 3: `N2 N2 N4`, onset `[0,2,4]`.
- 세 답 모두 길이 8u·발음 3회·쉼 0u. 답 배열 순서의 동일성 대신 재고·전체 덮음·음 종류·길이 조건을 검사한다.
- 오답 A: `N4 N4` → 길이는 맞지만 재고와 발음 횟수가 다름. “한 마디 길이는 맞아요. 이번 재료는 2분음표 하나와 4분음표 둘이에요.”
- 오답 B: N4를 두 번 탭해야 한다고 예측 → “긴 조각도 소리는 처음 한 번 시작해요. 이어지는 동안에는 새로 치지 않아요.”
- 확인 질문: “2분음표 한 개와 4분음표 두 개의 차이는?” 정답: 총 길이는 같고 시작 횟수가 다름.
- 추가 탐색: 통과 후 “다른 답 찾기”. 세 답을 모두 찾아야 다음으로 가는 조건은 없다.

### L5 쉼의 자리를 바꾸기

- 목표: LO3·LO5. 총 길이와 재료를 고정한 채 리듬을 바꾼다.
- 주문: “4분음표 세 개와 4분쉼표 하나를 써요. 첫 박은 소리로 시작하고, 원래와 다른 박에서 쉬게 해 주세요.”
- 비교 원본 A: `N2 N2 R2 N2`.
- 재고: N2 세 개, R2 한 개. B는 빈칸. 같은 박자·같은 템포.
- 정답 1: `N2 R2 N2 N2`, onset `[0,4,6]`, 쉼 `[2,4)`u.
- 정답 2: `N2 N2 N2 R2`, onset `[0,2,4]`, 쉼 `[6,8)`u.
- 통과 조건: 8u 전체, 재고 일치, 첫 이벤트 note, 원본과 쉼 구간 다름. 정확한 해답 수는 2개다.
- 오답 A: 원본과 같음 → “길이와 재료는 맞아요. 쉼표를 다른 박으로 옮겨 새 리듬을 만들어 보세요.”
- 오답 B: `R2 N2 N2 N2` → “다른 리듬을 만들었어요. 이번 주문에는 첫 박을 소리로 시작한다는 조건도 있어요.”
- 확인 질문: “두 버전에서 유지된 것은?” 총 길이와 소리 시작 횟수. 바뀐 것은 쉼과 시작 시점.
- 직접 치기: 학습자가 만든 정답을 따라 한다. 모델 정답 하나로 탭 목표를 강제하지 않는다.

### L6 반 박의 빈자리 듣기

- 목표: LO2·LO3·LO4·LO6. 음 길이와 쉼을 함께 식별한다.
- 주문: “모델을 듣고 같은 한 마디를 조립해 주세요. 처음에는 반 박 쉬어요.”
- 모델: `R1 N1 N2 N1 R1 N2`. 실제 이벤트는 다음과 같다.

| 시작 u | 종류 | 길이 u | 의미 |
| --- | --- | --- | --- |
| 0 | rest | 1 | 첫 박의 앞 반 박 쉼 |
| 1 | note | 1 | 첫 박의 뒤 반 박 소리 |
| 2 | note | 2 | 두 번째 박 전체 소리 |
| 4 | note | 1 | 세 번째 박의 앞 반 박 소리 |
| 5 | rest | 1 | 세 번째 박의 뒤 반 박 쉼 |
| 6 | note | 2 | 네 번째 박 전체 소리 |

- onset `[1,2,4,6]`, 소리 6u, 쉼 2u, 발음 4회. 기본 60 BPM, 원하면 50~100 BPM.
- 팔레트: N1·N2·R1·R2. 모델 듣기는 횟수 제한 없음. 첫 재생 전에도 듣기 안내를 제공한다.
- 통과 조건: 정규화한 음의 시작·지속 길이 및 쉼 구간이 모델과 같음. onset만 같아서는 통과하지 않는다.
- 오답 A: `R1 N1 N2 N2 N2` → onset은 같지만 세 번째 박 뒤 반 박이 소리로 채워짐. “시작하는 순간은 맞아요. 세 번째 박 뒤쪽은 소리가 멈추는 구간이에요.”
- 오답 B: `N1 R1 N2 N1 R1 N2` → 첫 반 박의 소리·쉼 순서가 뒤집힘. “모델은 처음에 반 박 쉰 다음 소리가 나요.”
- 오답 C: `R2 N2 N2 N2` → 같은 전체 길이지만 첫 소리의 시작이 늦음. 첫 박만 격자와 함께 비교한다.
- 힌트 1: 모델의 첫 박만 반복. 힌트 2: 1박과 3박을 나눠 비교. 힌트 3: 해당 한 박의 길이 표시. 전체 악보 보기는 assisted 해답 보기로 기록한다.
- 접근 경로: 소리 사용이 어려우면 “모델 기호 보기”로 전환하여 시각 조립 완료로 기록한다. 청음 평가 완료로 기록하지 않는다.
- 직접 치기: 목표 4회. 타이밍이 맞아도 오답 A의 지속·쉼 차이가 검증되었다고 처리하지 않는다.

## 10 자유 조립과 비교실

자유 조립은 첫 튜토리얼 이후 언제든 접근 가능하다. 전체 퍼즐 완료를 요구하지 않는다. 처음에는 빈 4/4 한 마디, 80 BPM, N2 선택 상태로 시작한다. 미완성 초안도 저장할 수 있다.

- 팔레트: N1·N2·N4·N8, R1·R2·R4·R8. 조각 수 제한 없음, 시간 예산 8u.
- 템포: 40~140 BPM, 1 BPM 간격의 입력과 ± 버튼. 재생 중 바꾸면 다음 재생에 적용한다.
- 길이 요약: “채운 길이 3박 / 전체 4박”, “소리 2.5박 · 쉼 0.5박 · 미정 1박”. 세 값 합이 항상 4박이다.
- 발음 횟수: semantic note group의 개수. 표기 fragment 개수와 다르다.
- A/B 비교: 현재 것을 A로 보관하고 B 편집. A와 B의 총 길이·onset·쉼·음 길이 차이를 따로 표시한다.
- 저장 슬롯: 기본 20개, 정렬은 최근 수정순. 슬롯이 차면 자동 삭제하지 않고 내보내기 또는 사용자가 고른 슬롯 교체를 안내한다.
- 파일 내보내기: 하나의 리듬 또는 전체 기록 JSON. 오디오 파일·이미지·공개 링크 내보내기는 후속.
- “모두 비우기”: 현재 초안만 비우고 undo 가능. 영구 저장 전체 삭제는 별도 설정 화면에서 명확히 확인한다.

완성된 모든 쉼 마디는 합법적인 조립품이다. “소리가 없는 한 마디예요”를 보여 주고, 두드리기는 “이번 마디에는 눌러야 할 소리가 없어요”라는 침묵 연습으로만 제공한다. 정확도 100점이나 0점으로 계산하지 않는다.

## 11 모바일 화면과 입력 설계

### 11.1 화면 목록

| 화면 ID | 내용 | 주 행동 | 이탈·복귀 규칙 |
| --- | --- | --- | --- |
| HOME | 이어하기, 퍼즐 6개, 자유 조립 | 시작·이어하기 | 저장된 초안 복원 |
| SETUP | 소리 허용, 볼륨, 선택적 보정 | 시작 | 건너뛰기 허용 |

| PERFORM | 카운트인, 목표 표시, 큰 탭 패드 | 연습 | 중단하면 이번 탭 기록 무효 |

### 11.2 BUILD 세로 배치

상단에서 아래 순서로 구성한다.

1. 뒤로가기, 문제 이름, 도움말. 높이 최소 48 CSS px.
2. 주문 한두 문장, 펼칠 수 있는 조건 목록. 읽지 않아도 추측하게 만들지 않는다.
3. 박자표 4/4, 템포, 채운 길이. 박자표에는 “4분음표를 한 박으로, 한 마디에 4박” 설명 버튼.
4. 박 번호와 한 마디 시간 막대. 조각에 음표·쉼표 기호와 길이 표시.
5. 선택 조각의 정보 및 이동·삭제·나누기 버튼.
6. 팔레트. 소리/쉼 전환은 탭 두 개로 분리하되 마지막 선택을 유지한다.
7. 하단 행동: 듣기 / 정지 / 확인. 화면 아래 safe-area를 반영한다.

최소 320 CSS px 화면에서 8칸을 각각 44px로 만들면 352px가 필요하므로 한 줄의 모든 칸을 억지로 44px라고 주장하지 않는다. 시각 격자는 축소 가능하지만 실제 기본 배치는 아래의 “박 선택 → 앞/뒤 반 박 선택” 2단계 터치 컨트롤로도 완전히 수행할 수 있게 한다. 이 컨트롤의 버튼은 최소 44×44 CSS px이며 간격 8px를 둔다. 넓은 화면의 직접 칸 탭은 보조 빠른 조작이다.

8칸에 가로 스크롤이 필요하면 박 번호와 현재 선택을 유지하고 별도의 확대 보기로 제공한다. 핵심 버튼을 가로 스크롤 밖으로 숨기지 않는다. 화면 회전 때 입력·재생을 중단하고 조립 상태만 유지한다. 한 마디를 두 줄로 쪼개 보여 주어 박 진행을 오해하게 하는 기본 레이아웃은 피한다.

### 11.3 탭 기반 편집의 정확한 동작

1. 팔레트 조각 탭: `selectedTool` 설정, 음가 이름과 차지할 칸 수 읽어 줌.
2. 빈 시작 칸 탭: 끝 위치까지 여유가 있으면 ghost 미리보기 표시. 기본은 한번 탭으로 배치하되 설정에서 “배치 확인 사용”을 켤 수 있음.
3. 기존 조각 탭: 선택만 한다. 덮어쓰기나 삭제는 일어나지 않음.
4. 선택 조각 이동: “옮기기” → 빈 시작 칸 탭. 원래 위치를 임시로 비운 전체 초안에 배치 가능성을 검사.
5. 길이 바꾸기: 선택 → 길이 버튼. 늘어난 구간이 겹치면 거부, 주변 조각을 자동으로 밀지 않음.
6. 삭제: 선택 → 삭제. 빈칸이 생기며 자동 쉼표 변환 없음.
7. 나누기: N2→N1+N1, N4→N2+N2, N8→N4+N4. 발음이 추가됨을 미리 안내. 쉼표 나누기는 침묵 길이만 유지.
8. 합치기: 인접 쉼표의 합이 지원 음가 1/2/4/8u 중 하나인 경우에만 MVP 편집 병합 허용. 예를 들어 R1+R1→R2는 가능하고 R1+R2→R3는 아직 불가. 정답 비교용 canonical 침묵 span은 임의의 인접 쉼 길이를 합칠 수 있지만 원본 이벤트를 바꾸지 않는다. 인접 음 병합은 재발음을 없애므로 MVP에서 제공하지 않음.

### 11.4 선택적 드래그

Pointer Events로 구현한다. 터치 시작 즉시 스크롤을 빼앗지 않으며 팔레트와 편집 영역에 한정된 명시적 드래그 핸들을 사용한다. 드래그 시작 임계값 8px, ghost는 손가락 위 32px에 표시하고 현재 시작 박을 텍스트로 함께 읽는다. 이 수치는 사용성 실험으로 조정할 초기값이다.

`pointercancel`, `lostpointercapture`, 화면 회전, 탭 숨김에서는 원본으로 복원한다. 드롭 시 전체 작업을 하나의 transaction으로 commit한다. 잘못된 드롭은 이전 상태를 유지한다. 동시에 여러 손가락으로 조각을 이동하지 않는다. [W3C Pointer Events](https://www.w3.org/TR/pointerevents3/)의 이벤트 모델을 기반으로 하되 최신 구현 여부는 실기기에서 검사한다.

### 11.5 접근성

드래그에는 클릭·탭만 사용하는 대체 경로가 필요하다. 키보드 대안만으로 단일 포인터 대안 요구를 충족했다고 보지 않는다. 본 앱의 44px 버튼 목표는 제품 자체 기준이며, WCAG 2.2 AA의 최소 타깃 기준을 44px라고 잘못 인용하지 않는다. 관련 공식 기준은 [Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)와 [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)이다.

- 의미 있는 HTML 버튼을 기본으로 하고 SVG 기호만을 클릭 대상으로 삼지 않는다.
- 키보드: Tab으로 영역 이동, 방향키로 시작 칸 이동, Enter 배치·선택, Delete 삭제, Escape 취소, Ctrl/Cmd+Z 되돌리기. Space는 포커스가 탭 패드일 때만 연주한다.
- 편집 grid에는 roving tabindex와 `aria-label`을 사용하되 실제 스크린리더로 확인한다. 대체 목록형 편집 UI를 항상 제공한다.
- 읽기 예: “두 번째 박 앞, 4분음표, 한 박 길이, 선택됨”. 이어지는 칸은 “앞 음의 지속 구간”이라고 설명한다.
- 색만으로 소리·쉼·오류를 구분하지 않는다. 소리에는 채운 원과 음표, 쉼에는 빗금과 쉼표, 미정에는 점선 테두리.
- 성공·오류 안내는 `aria-live=polite`. 오디오 재생 중 매 프레임 박 위치를 읽어 주지 않는다.
- 텍스트 200% 확대, 320px 폭 reflow, OS 동작 줄이기, 고대비·다크 모드에서 기능을 유지한다.
- 번쩍임·화면 흔들림·실패음 폭발을 사용하지 않는다. 진동은 선택 보조이며 지원하지 않아도 기능 손실이 없어야 한다.
- 청각 없이 조립·이론 확인 가능. 시각 없이도 목록 조립·음성 레이블·듣기 가능. 특정 감각의 평가를 수행하지 않은 경우 결과에 이를 구분한다.

## 12 판정과 피드백 계약

### 12.1 구조 검증 순서

편집 중 실시간 검증은 부드러운 안내이며 제출 판정과 분리한다. 제출 시 순서는 고정한다.

1. 스키마·ID·정수 범위·지원 음가 확인
2. 시작/끝이 마디 안인지 확인
3. 겹침 및 금지된 잠금 수정 확인
4. 전체 마디의 빈칸 여부 확인
5. 문제의 팔레트·재고·위치·순서·소리/쉼 조건 확인. 팔레트는 새로 생성하거나 변형한 조각에 적용한다. 콘텐츠가 제공한 원본 그대로의 초기·잠금 조각은 팔레트에 없어도 유지 가능하다. 따라서 L2의 잠긴 N2 세 개는 정상이다. 재고 조건은 명시된 전체 문서를 검사하며 L2는 최종 N2 세 개와 N1 두 개로 정의한다.
6. semantic rhythm 비교 또는 조건식 평가
7. 이번 과제의 설명 질문 확인

시스템 데이터 오류를 학습자 오답으로 저장하지 않는다. 잘못된 JSON이나 콘텐츠 정의는 `contentError`로 별도 분기하며 문제 제출을 중지한다.

### 12.2 의미 정규화

`canonicalize`는 이벤트를 시작 시각순으로 정렬하고, 인접한 쉼표만 하나의 침묵 span으로 병합한다. 음표는 같은 pitch라고 해도 붙임줄이 없는 한 병합하지 않는다. 붙임줄 지원 후에는 유효한 tie chain만 하나의 sounding event로 묶는다. 정규화는 원본 편집 표시를 덮어쓰지 않는다.

리듬 비교 값은 `[{kind, startTick, durationTick, pitch?}]`의 정규화 배열이다. 필요에 따라 onset signature와 silence signature를 별도 산출하지만, 음가까지 묻는 문제의 정답 판정은 full signature를 사용한다. 색·ID·조각 생성 순서·화면 좌표는 정답에 영향을 주지 않는다.

다중 정답 문제 L4·L5는 허용 답을 하나로 고정하지 않고 명시적 constraint를 검사한다. 콘텐츠 CI에서는 모든 작은 조합을 열거하여 예상 답 개수와 일치하는지 확인한다. 조건식을 문자열 `eval`로 실행하지 않고 허용된 연산자들의 JSON AST로 표현한다.

### 12.3 결과 표시

결과 카드는 다음 순서다.

- “한 마디 길이: 맞아요” 또는 “반 박이 남았어요”
- “주문 조건: 2개 중 1개 충족”과 구체적인 조건
- “이번에 확인한 개념” 한 문장
- 선택적 직접 치기 결과: 맞춘 시작 수/전체 시작 수, 조금 빠름·늦음, 추가 입력 수
- “다시 조립”, “다른 답”, “직접 치기”, “다음” 중 상황별 버튼

이론 화면에 별 세 개 총점이나 탭 점수를 섞지 않는다. 내부 상태는 `structurePass`, `objectivePass`, `explanationPass`, `assistance`로 구분한다. 진행 해금은 구조+목표 통과로 한다. 설명 질문은 답과 근거를 확인할 때까지 안내하지만 별도 패널로 보존하며 탭 점수는 어떤 해금에도 쓰지 않는다.

## 13 애플리케이션 구조

### 13.1 제안 스택과 선택 이유

TypeScript·React·Vite로 정적 SPA를 만들고, 오디오는 브라우저 Web Audio API를 직접 감싼 작은 어댑터로 구현한다. 한 마디·한 악기 범위에 서버나 대규모 게임 엔진을 먼저 도입할 필요는 없다. React는 화면 상태에 쓰고 음원 예약·입력 timestamp의 소유자가 되지 않게 한다. 프레임마다 React state를 갱신하여 오디오를 구동하지 않는다.

버전은 실제 착수 시 공식 안정 버전을 확인하고 lockfile로 고정한다. 이 문서는 확인하지 않은 “최신 버전 번호”를 적지 않는다. 빌드·테스트 도구 사용법은 [React 공식 학습 자료](https://react.dev/learn), [Vite 가이드](https://vite.dev/guide/), [Vitest 가이드](https://vitest.dev/guide/), [Playwright 가이드](https://playwright.dev/docs/intro)를 기준으로 구현 시 재확인한다.

도메인 코드는 UI·DOM·오디오·저장소에 의존하지 않는 순수 함수로 작성한다. 앱을 다른 렌더러로 옮겨도 음악 판정은 유지되어야 한다.

## 14 오디오 엔진과 시간 동기화

### 14.1 표준 근거와 구현 한계

Web Audio는 `AudioContext.currentTime` 기준 예약 재생과 파라미터 자동화를 제공한다. `getOutputTimestamp()`는 오디오 출력 위치와 `performance.now()` 계열 시간의 대응을 제공하고, `baseLatency`는 전체 기기·인간 반응 지연을 뜻하지 않는다. 정의는 [W3C Web Audio 2021 Recommendation](https://www.w3.org/TR/2021/REC-webaudio-20210617/#dom-audiocontext-getoutputtimestamp)을 근거로 한다. 해당 문서의 오래된 브라우저 지원 표는 현재 호환성 표로 재사용하지 않는다. 2026년 Web Audio 1.1은 확인 당시 Working Draft이므로, 초안의 기능 전체를 출시 전제조건으로 삼지 않는다.

아래 예약 간격·보정 횟수·허용 지연값은 본 앱의 설계 결정이다. 모든 브라우저나 무선 이어폰에서 동일 정확도를 보장한다는 뜻은 아니다.

### 14.2 음색과 엔벌로프

첫 악기는 직접 합성한 부드러운 지속음이다. 예시 구현은 기본 주파수 약 261.63Hz의 sine에 낮은 레벨의 2차 배음을 더하고, note별 GainNode 엔벌로프를 둔다. 녹음 샘플을 사용하지 않아도 시작·지속·쉼을 구별할 수 있다. 비교 과제에서는 악기·음량·음높이를 고정한다.

- attack: 5ms의 짧은 ramp
- sustain: semantic note의 대부분 길이를 유지
- release: 최대 15ms, 단음 길이의 10% 이하, 이벤트 끝 시점에 0이 되도록 끝에서 역산
- stop: semantic endTime 이후 안전한 짧은 여유를 두되 gain은 이미 0
- 기본 master gain: 0.18 제안, 실제 음량은 기기별 청취 점검 후 결정
- 노트·메트로놈·UI 소리를 별도 gain bus로 분리
- 피크 합산 헤드룸 확보, 클리핑 탐지 테스트, 갑작스러운 노드 절단 금지

지속 길이와 악기의 실제 진폭 모양은 완전히 같은 개념이 아님을 개발자가 이해해야 한다. 이 학습 음색은 비교를 돕기 위해 지속 구간이 들리도록 만든다. 리버브·딜레이·긴 잔향은 MVP에서 제외한다. 쉼표 직전 음의 tail이 쉼을 덮지 않게 한다.

직접 치기의 즉시 피드백은 같은 음색의 80ms 단음으로 낼 수 있으나, 이는 사용자의 실제 길이 연주를 기록한 결과가 아님을 표시한다. “예시 소리 따라 치기” 중에는 목표 음원 재생 여부를 선택할 수 있고 메트로놈은 별도 조절한다.

### 14.3 템포 계산

템포는 BPM 숫자만 저장하지 않고 기준 음가도 함께 저장한다.

```ts
type Fraction = { num: number; den: number };
type Tempo = { bpm: number; beatUnit: Fraction }; // 온음표 대비 비율
const PPQ = 480;
function ticksFromWholeFraction(f: Fraction): number {
  const scaled = 4 * PPQ * f.num;
  if (!Number.isSafeInteger(scaled) || scaled % f.den !== 0) {
    throw new Error('UNSUPPORTED_RATIONAL_DURATION');
  }
  return scaled / f.den;
}
function qpm(t: Tempo): number {
  return t.bpm * 4 * t.beatUnit.num / t.beatUnit.den;
}
function secondsForTicks(ticks: number, t: Tempo): number {
  return ticks / PPQ * 60 / qpm(t);
}
```

실제 함수는 분모 양수·분자 정수·BPM 범위·NaN·무한대 검증을 먼저 한다. 4/4에서 4분음표=80 BPM이면 한 마디는 3초, 한 칸은 0.375초다. 6/8에서 점4분음표=80 BPM이면 한 마디는 1.5초이고 8분음표 한 칸은 0.25초다. 박자 숫자가 같거나 BPM 숫자가 같다고 마디의 초 길이가 항상 같은 것은 아니다.

### 14.4 예약 재생

MVP는 한 마디가 짧으므로 카운트인과 최대 4회 반복을 한 세션 시작 때 미리 예약한다. 일반 `setInterval`에서 매 순간 소리를 새로 내는 방식은 금지한다. UI 애니메이션은 `requestAnimationFrame`으로 현재 오디오 출력 위치를 읽어 표시할 뿐이다.

1. 사용자 재생 동작에서 context 생성/resume을 요청한다.
2. 실제 `state === running`이고 시간축이 진행되는지 확인한다. 브라우저 자동재생 제한은 [Chrome 공식 정책 설명](https://developer.chrome.com/blog/autoplay/)처럼 사용자 동작에 영향을 받을 수 있으므로 무조건 자동재생을 가정하지 않는다.
3. `runId`를 새로 발급하고 immutable rhythm snapshot을 확정한다.
4. `audioStart = currentTime + 0.15`초로 카운트인을 예약한다. 0.15초는 초기 안전 여유이며 기기 시험으로 조절한다.
5. `barStart = audioStart + countInDuration`으로 본 마디 시작을 확정한다.
6. 모든 note start/end·메트로놈·반복을 `barStart + secondsForTicks(...)`로 계산한다. 반복마다 앞 시간에 덧셈을 누적하지 않고 `barStart + loopIndex * barDuration + eventOffset`을 사용한다.
7. note/rest와 별개로 시각 cursor의 0~1920tick 진행을 계산한다.
8. 종료 시 모든 노드를 dispose하고 `runId` 일치 여부 확인 후 결과를 반영한다.

반복 듣기는 기본 1회, 선택 2회·4회다. 채점하는 직접 치기는 한 마디 1회로 고정하므로 목표는 최대 8개다. 다시 치기는 새 runId로 시작한다. 무한 반복·재생 중 템포 변경은 MVP에 없다. 필요하면 후속에서 25ms 점검/100~150ms lookahead의 scheduler를 추가하되 음악 시간 자체는 오디오 시계로 계산한다.

일반 타이머 지연이 음원 예약 시각을 결정하지 않도록 하고, completion 타이머가 늦어져도 이미 예약된 음원은 진행한다. 긴 메인스레드 정지로 입력 신뢰도가 깨진 세션은 탭 평가를 무효화할 수 있다.

### 14.5 출력 시계 매핑

지원되는 경우 매핑은 다음과 같이 정의한다. `c0`는 `getOutputTimestamp().contextTime`(초), `p0`는 `performanceTime`(ms), 목표 오디오 시각이 `a`라면 예상 출력 시각은 `P(a) = p0 + 1000 × (a - c0)`이다. 유효하지 않은 0/0 값, 과도하게 오래된 표본, 역행하는 시간은 사용하지 않는다.

매 프레임 또는 약 100ms 간격으로 매핑 표본을 갱신하고 입력 시점에 가까운 표본으로 비교한다. 한 세션에서 목표마다 서로 다른 기준을 섞더라도 같은 오디오 timeline에 대한 매핑이어야 한다. 시계 오차를 감지하면 그 세션을 중단하고 재시작한다.

`getOutputTimestamp`가 없거나 불안정하면 `currentTime`과 `performance.now()`를 최대한 가까이 읽은 anchor로 매핑한다. 이 fallback은 출력 지연을 정확히 제거하지 못하므로 사용자 보정이 포함된 연습용 모드로 표시한다. `baseLatency`와 `outputLatency`를 무조건 더하거나, 출력 매핑을 이미 쓴 뒤 또 빼는 이중 보정은 금지한다.

### 14.6 입력 시각과 보정의 부호

탭은 `pointerdown`의 `event.timeStamp`를 우선 사용하되 현재 `performance.now()` 기준과 같은 시간 원점인지 sanity check한다. 값이 비정상적이면 처리 시각을 fallback으로 사용하고 신뢰도를 낮춘다. 정상 timestamp의 경우 `performance.now()-event.timeStamp`가 150ms를 넘는 입력이 있으면 입력 큐 지연으로 해당 연습을 invalidated 처리한다. 이 150ms는 초기 제품 기준이며 실기기 검증 후 gradingVersion과 함께 조정한다. 마우스 클릭의 `click`과 touch의 `pointerdown`을 동시에 채점하지 않는다.

보정 잔차는 `rawErrorMs = inputPerformanceMs - expectedOutputPerformanceMs`다. 양수는 늦게 들어온 입력이다. 보정값 `calibrationOffsetMs`는 유효 보정 탭의 rawError 중앙값이다. 실제 오차는 `correctedErrorMs = rawErrorMs - calibrationOffsetMs`로 계산한다. 예: 목표 1000ms, 탭 1120ms, 보정값 +100ms → 보정 오차 +20ms.

이 보정에는 브라우저/기기 경로와 사용자의 일관된 움직임 성향이 함께 들어갈 수 있다. “기기의 정확한 지연”이라고 이름 붙이지 않고 “내 입력 맞춤”으로 표현한다. 마이크를 사용하지 않는다.

### 14.7 보정 절차

- 4분음표=80 BPM의 클릭을 듣고 4회 익숙해진 뒤 12회 탭한다.
- 목표 하나에 탭 하나를 대응시킨다. ±350ms 밖 탭·중복 입력을 제외한다.
- 유효 탭이 8개 미만이면 보정하지 않고 재시도/건너뛰기를 제공한다.
- 1차 median과 MAD를 구한다. `|error - median| > max(3×MAD, 60ms)`를 이상치로 제외하고 중앙값을 다시 구한다.
- MAD가 45ms를 넘거나 유효 표본이 8개 미만이면 “입력 간격이 일정하지 않아 맞춤값을 저장하지 않았어요.”라고 안내한다.
- 저장 범위는 -250~+250ms. 밖의 값은 잘라 저장하지 않고 출력 장치·연결 변경 확인을 요청한다.
- 매핑 방식(native/fallback), sampleRate, 보정 시각, 선택한 “내장 스피커/유선/무선/기타” 라벨만 로컬 저장한다. 기기 fingerprint·장치 ID를 수집하지 않는다.
- 출력 변경을 감지하거나 사용자가 이어폰을 바꿨다고 선택하면 기존 보정을 `stale`로 표시하고 재보정 안내. clockMode 또는 sampleRate가 달라져도 stale로 처리하고 다른 시계 방식의 보정값을 재사용하지 않는다. 자동 감지는 완전하지 않으므로 설정에 언제든 보정 재실행 버튼을 둔다.
- 보정하지 않아도 조립과 선택적 연습은 가능하다. 정밀도 낮음 표시와 넓은 연습용 판정만 제공한다.

### 14.8 오디오 중단과 음소거

`visibilitychange`로 숨김, 화면 잠금, 전화·OS 중단, context가 running이 아닌 상태, 출력 장치 변경은 현재 연주 세션을 중단한다. 예약 노드를 전부 취소하고 gain을 짧게 내려 클릭을 방지한다. 이미 오디오가 계속되었을 가능성이 있으므로 재개 시 중간 지점부터 채점을 이어 가지 않는다. “처음부터 다시 듣기/치기”를 제공한다.

무음 스위치·시스템 음량 상태를 확실하게 알 수 없는 브라우저에서는 원인을 단정하지 않는다. “소리가 들리나요?” 선택과 일반적인 기기 음량 확인 안내를 제공한다. 실패해도 저장·이론 조립 경로는 계속 사용할 수 있다.

## 15 직접 치기 판정

### 15.1 무엇을 평가하는가

완성된 snapshot의 sounding event onset만 목표다. 쉼표와 긴 음의 지속 중간에는 탭 목표를 만들지 않는다. L4 `N4 N2 N2`의 목표는 `[0,4,6]`u의 3개이며 2분음표를 두 번 누르게 하지 않는다.

정답이 여러 개면 사용자가 제출하여 통과한 snapshot에서 목표를 생성한다. 고정된 모범 답의 target을 재사용하면 안 된다. 결과에는 `rhythmHash`·`runId`·템포·보정 프로필 버전이 함께 기록된다.

### 15.2 유효 입력 수집

- 입력 수집 listener는 COUNT_IN부터 준비한다. 각 입력은 `correctedInputTime = rawInputPerformanceMs - calibrationOffsetMs`로 변환하고, 본 마디 출력 시작 P(barStart) 기준 상대 시각이 `[-W, barDurationMs+W]`에 있을 때만 평가 후보로 받는다. 그 밖의 카운트인 탭은 채점하지 않는다. 카운트인 끝 이전이어도 이 창에 들어오는 입력은 보존한다.
- raw 시각의 동등한 수집 범위는 `[P(barStart)-W+offset, P(barEnd)+W+offset]`다. 예를 들어 offset=-250ms일 때 이른 보정 입력을 고정 raw 창으로 버리면 안 된다.
- 청각 재생은 barEnd에 끝나지만 평가 확정은 raw 수집 종료와 barEnd 중 더 늦은 시각까지 기다린다. 동일한 performance ms 좌표에서 `closePerformanceMs = max(P(barEnd), P(barEnd)+W+offset)`으로 계산하며 이를 INPUT_WINDOW_CLOSED로 알린다. 끝 grace에 들어온 입력도 목표와 매칭되지 않으면 추가 입력이다.
- 같은 `pointerId`의 down이 up/cancel 없이 반복되면 중복으로 무시한다. 두 손가락의 실제 다른 입력은 별도로 기록하여 중복 난타를 숨기지 않는다.
- keyboard `repeat`는 무시한다. 포커스가 탭 패드에 있을 때만 Space/Enter를 입력으로 사용하고 페이지 스크롤을 막는다.
- 프레임 드롭·탭 숨김·context interruption이 감지된 세션은 `invalidated`로 저장하고 성적 계산하지 않는다.
- 1회 시도 최대 입력 64개. 초과하면 난타를 유도하는 점수 대신 “입력이 너무 많아 이번 기록은 계산하지 않았어요”로 종료한다.

### 15.3 허용 창과 매칭

목표 간 최소 간격을 `minIOIMs`로 계산한다. 목표가 하나면 한 마디 길이를 사용한다. 기본 허용 창은 `W = min(160ms, 0.45 × minIOIMs)`다. 아주 근접한 구간은 `G = min(55ms, 0.5 × W)`다. 경계값은 `<=`로 포함한다. 이 수치는 초기 제품 기준이며 학습자·기기 시험에서 조정하되 콘텐츠 버전과 별도로 `gradingVersion`에 남긴다.

예: 4분음표=120 BPM, 연속 8분음표 간격 250ms이면 W=112.5ms, G=55ms다. 4분음표=140 BPM이면 8분 간격 약 214.286ms, W≈96.429ms다. 인접 목표의 허용 창이 겹치지 않도록 0.5보다 작은 계수를 사용한다.

매칭은 시간 순서를 보존하는 동적 계획법으로 한다. 목적은 첫째 유효 match 수 최대, 둘째 전체 절대 오차 최소다. 하나의 입력을 둘 이상의 목표에 배정하지 않고, 목표 하나에 여러 입력을 배정하지 않는다. 동률이면 더 이른 목표·더 이른 입력을 고른다. 단순히 가까운 목표를 탐욕적으로 고르는 구현은 별도 반례 검사를 통과해야 한다.

```text
입력: 정렬된 목표 target[0..N), 보정된 tap[0..M), 허용창 W
DP[i][j]는 앞 i개 목표와 앞 j개 입력을 처리한 최선 상태
전이 A: 목표 i를 놓침으로 처리
전이 B: 입력 j를 추가 입력으로 처리
전이 C: abs(tap[j]-target[i]) <= W일 때 한 쌍 match
비교: match 수가 큰 상태 우선, 같으면 총 absError가 작은 상태
결과: match 목록, miss 목록, extra 목록, 각 errorMs
```

MVP에서 N≤8, M≤64이므로 이 계산은 작다. W 계산에 오디오 envelope 길이나 note duration을 잘못 사용하지 않는다. 같은 긴 음의 중간 탭은 별도 목표가 없으므로 추가 입력이다.

### 15.4 결과와 쉼 구간의 입력

“시작 4개 중 3개를 맞췄어요. 추가 입력 1번.”처럼 사실을 먼저 보여 준다. match마다 정확/조금 빠름/조금 늦음을 표시하고 오차 숫자는 펼쳐 볼 수 있게 한다. 원하면 오차 막대와 목표 박을 함께 보여 준다.

추가 입력이 명시적 쉼 span 내부에 있고 어떤 목표 허용 창에도 매칭되지 않았으면 “쉬는 구간에서 입력”으로 분류한다. 허용 창 안에서 다음 음을 조금 일찍 누른 것을 이론적 쉼 오답과 중복 집계하지 않는다. 이 지표도 운동 수행 설명이며 L3·L6의 구조 정답을 취소하지 않는다.

목표 0개인 마디는 `notApplicable`이다. 보정 미완료·fallback·높은 입력 큐 지연이면 `practiceOnly` 또는 `lowConfidence`다. 낮은 신뢰도를 학습자의 “낮은 실력”과 같은 색·레이블로 표시하지 않는다. 랭킹과 타 사용자 비교는 없다.

## 16 상태 머신과 이벤트 계약

### 16.1 주요 상태

```text
BOOT
  -> LOADING_LOCAL
  -> HOME 또는 RECOVERY
HOME
  -> AUDIO_SETUP (선택)
  -> TUTORIAL
  -> EDITING
EDITING
  -> PREVIEW_PREPARING -> COUNT_IN -> PREVIEW_PLAYING -> EDITING
  -> VALIDATING -> FEEDBACK -> EDITING 또는 THEORY_PASSED
THEORY_PASSED
  -> PERFORMANCE_PREPARING -> COUNT_IN -> PERFORMING -> PERFORMANCE_RESULT
  -> HOME 또는 다음 EDITING
모든 재생 상태
  -> INTERRUPTED -> EDITING 또는 THEORY_PASSED
복구 불가능한 콘텐츠 오류
  -> CONTENT_ERROR -> HOME
```

`COUNT_IN`은 `purpose: preview | performance | calibration`을 갖는다. 카운트인 종료가 무조건 PERFORMING으로 가는 버그를 방지한다. 저장은 orthogonal 상태 `clean | pending | saving | failed`로 관리하고, 저장 실패가 재생 상태를 임의로 바꾸지 않는다.

### 16.2 전이 표

| 현재 | 이벤트 | guard | 효과 | 다음 |
| --- | --- | --- | --- | --- |
| EDITING | PLACE_PIECE | 범위·겹침·잠금 검사 | 명령 commit, revision+1, 저장 예약 | EDITING |
| EDITING | PLAY_PREVIEW | 유효 데이터, context 준비 | snapshot·runId 생성 | PREVIEW_PREPARING |
| PREVIEW_PREPARING | AUDIO_READY | runId 일치 | 카운트인 예약 | COUNT_IN |
| COUNT_IN | COUNT_IN_ENDED | purpose와 runId 일치 | 본 연주 화면으로 전환하며 입력 수집 유지, 또는 preview 활성 | 목적별 상태 |
| EDITING | SUBMIT | schema 정상 | 순수 판정 실행 | VALIDATING |
| VALIDATING | VALIDATION_DONE | snapshot revision 일치 | 결과 저장 | FEEDBACK |
| FEEDBACK | ACCEPT_EXPLANATION | 구조·목표 통과 | 진도 commit | THEORY_PASSED |
| PERFORMING | TAP | runId 일치, 유효 입력 | timestamp append | PERFORMING |
| COUNT_IN | TAP | purpose=performance, 보정된 수집창 안 | timestamp append, 아직 화면은 카운트인 | COUNT_IN |
| PERFORMING | BAR_COMPLETE | runId 일치 | 재생 표시 종료, 잔여 입력창 유지 | PERFORMING |
| PERFORMING | INPUT_WINDOW_CLOSED | runId 일치, barEnd와 raw창 종료 모두 경과 | 매칭·결과 계산 | PERFORMANCE_RESULT |
| 재생 중 | STOP 또는 HIDDEN | 항상 | gain fade, 노드 stop, runId 무효 | INTERRUPTED 또는 편집 |
| 임의 | SAVE_FAILED | 저장 revision 일치 | 경고·내보내기 제공 | 현재 상태 유지 |

설명 질문을 건너뛴 학습자가 이론 구조 통과 자체를 잃지 않도록 `objectivePass`와 `explanationReviewed`를 분리한다. 다음 문제 접근은 `objectivePass`로 해금하고 결과 패널에 확인 질문을 남긴다. 구현자가 표의 `ACCEPT_EXPLANATION`만 진도 저장 경로로 오해하지 않도록, `VALIDATION_DONE`에서 objectivePass를 먼저 저장한다.

### 16.3 동시성 규칙

- 모든 비동기 콜백에 `runId`와 `documentRevision`을 전달한다.
- 중지·이탈 후 도착한 이전 콜백은 무시한다.
- 재생 버튼 연타는 같은 pending 요청을 공유하거나 두 번째를 무시한다. AudioContext·카운트인·노드를 중복 생성하지 않는다.
- 데이터 저장은 revision 오름차순으로 직렬화한다. 늦게 끝난 과거 write가 최신 작업을 덮지 못하게 한다.
- undo는 하나의 semantic command 단위이며 최대 100단계 메모리 ring으로 보관한다. reload 후 undo 전체 복원은 MVP에 요구하지 않고 마지막 초안만 복원한다.
- 문제 이동 시 실행 중 오디오를 먼저 정지하고 초안 저장 transaction 결과를 확인한다. 실패하면 현재 초안을 메모리에 유지하고 사용자에게 내보내기 선택을 제공한다.
- 콘텐츠 업데이트를 플레이 도중 적용하지 않는다. 홈으로 돌아갔을 때 새 버전을 안내한다.

### 17.1 공통 타입

아래는 구현에 필요한 필수 필드의 TypeScript 계약이다. 실제 런타임에는 JSON schema 또는 동일한 강도의 validator를 두어 TypeScript 타입만 믿지 않는다.

```ts
type Tick = number; // 유한한 안전 정수, >= 0

type Meter = {
  numerator: number;
  denominator: 2 | 4 | 8 | 16;
  groupUnits: number[]; // 분모 음가 단위 묶음. 4/4=[1,1,1,1], 6/8=[3,3]
};

type RhythmEvent = {
  id: string;
  kind: 'note' | 'rest';
  startTick: Tick;
  durationTick: Tick;
  pitch?: 60;           // MVP note만 필수, rest에는 금지
  sourceValue: { num: number; den: number };
  tieNextId?: string;   // MVP 입력은 금지, 후속 migration을 위한 예약 필드
  locked?: boolean;
};

type RhythmDocument = {
  schemaVersion: 1;
  id: string;
  contentVersion: string;
  revision: number;
  ppq: 480;
  meter: Meter;
  tempo: { bpm: number; beatUnit: {num: number; den: number} };
  events: RhythmEvent[];
  title?: string;
  createdAt: string;
  updatedAt: string;
};

type Rule =
  | { op: 'fullCoverage' }
  | { op: 'inventory'; counts: Record<string, number> }
  | { op: 'firstKind'; kind: 'note' | 'rest' }
  | { op: 'sameSemanticRhythm'; referenceId: string }
  | { op: 'differentSilence'; referenceId: string }
  | { op: 'lockedUnchanged' };

type Puzzle = {
  id: string;
  version: number;
  title: string;
  prompt: string;
  tempo: { default: Tempo; minBpm: number; maxBpm: number };
  modelReferenceId?: string;
  objectiveIds: string[];
  meter: Meter;
  gridTick: 240;
  initialEvents: RhythmEvent[];
  palette: string[];
  constraints: Rule[];
  references: Record<string, RhythmEvent[]>;
  expectedAnswerCount: number;
  modelAvailable: boolean;
  hints: {level: 1|2|3; text: string; focus?: {startTick: Tick; endTick: Tick}}[];
  explanation: {prompt: string; options: {id: string; text: string}[]; correctId: string};
  expectedConcept: string;
};
```

`sourceValue`와 `durationTick`이 모순되면 데이터 오류로 거부한다. `locked`는 콘텐츠의 권위 있는 initialEvents와 비교하고, 가져온 파일에서 locked를 지웠다고 고정 조각을 바꿀 수 없게 한다. 반대로 자유 모드 문서의 잠금은 필요하지 않으므로 제거 가능하다.

### 17.4 데이터 불변 조건

- 모든 이벤트 ID는 문서 내 유일하다.
- `startTick % 240 === 0`, MVP duration은 240/480/960/1920 중 하나다.
- 끝은 `startTick + durationTick`이며 마디 범위 안이다.
- 이벤트는 반개구간 `[start,end)`을 차지한다. 맞닿은 경계는 겹침이 아니다.
- rest는 pitch를 가질 수 없다. note는 pitch=60을 가진다.
- `sum(groupUnits) === numerator`이며 큰 박/분할 UI는 groupUnits를 사용한다.
- 저장된 sourceValue의 분수가 durationTick과 정확히 일치한다.
- 퍼즐 초안에는 gap 허용, 완성 판정에는 gap 금지.
- 최대 한 마디·8개의 최소 길이 이벤트. 악의적 파일은 이 한도를 우회할 수 없다.
- 문서와 콘텐츠 버전은 별도다. 퍼즐 문구 변경 때문에 사용자의 작품 시간 구조가 달라지지 않는다.

## 18 저장과 오프라인 및 개인정보

### 18.1 로컬 저장

IndexedDB에 `settings`, `drafts`, `progress`, `compositions`, `metadata` object store를 둔다. 원자적 transaction을 이용한다. 비동기 객체 저장 API라는 근거는 [W3C Indexed Database API](https://www.w3.org/TR/IndexedDB-3/)이며, 아래 복구 정책은 앱의 설계 결정이다.

편집 명령 commit 후 300ms debounce로 최신 snapshot을 저장한다. 연속 입력 중에는 2초마다 강제 checkpoint를 예약한다. 화면 이탈·재생 시작·제출·저장 버튼 시 즉시 저장 요청을 하되, `beforeunload`에서 비동기 쓰기가 반드시 완료된다고 가정하지 않는다. 완료된 마지막 snapshot까지만 복구를 보장한다. UI에는 “저장 중”과 “이 기기에 저장됨”을 실제 transaction 결과에 따라 표시한다.

쓰기 시 `current`와 `previousGood`을 같은 transaction 안에서 관리한다. 새 문서의 스키마 검증 후 저장하고 읽어 다시 schema·revision을 확인한다. 복구 불능이면 previousGood으로 돌아갈지 사용자에게 제시하고 손상 원본을 덮어쓰지 않는다. 내보낼 수 있으면 손상 원본도 진단용으로 보존하되 자동 외부 전송은 하지 않는다.

### 18.2 다중 탭과 저장 충돌

MVP는 같은 origin의 편집 탭 하나만 writer가 되게 한다. BroadcastChannel은 탭 간 상태 알림에 사용하고, writer 권한의 획득·갱신·해제는 IndexedDB transaction의 lease owner와 단조 증가 fencing token으로 확정한다. 두 번째 탭은 읽기 전용 안내와 “여기서 편집하기” 버튼을 제공한다. 모든 쓰기에서 owner/token/revision을 재검사하고, 만료된 lease의 과거 writer는 쓰기를 중단한다. lease 만료와 탭 종료를 처리하며 단순 localStorage 플래그 하나만으로 영구 잠금을 만들지 않는다.

write transaction에서 저장된 revision을 비교하여 충돌하면 사용자 초안을 별도 복구 슬롯에 보관한다. 무조건 마지막 저장을 승자로 삼아 작품을 잃게 하지 않는다. 설정의 가벼운 충돌과 작품 충돌은 다른 정책을 사용할 수 있다.

### 18.3 JSON 내보내기와 가져오기

내보내기 파일에는 `exportFormat`, `schemaVersion`, `exportedAt`, `appVersion`, 문서 배열, 선택적 진도·설정이 들어간다. 기기 식별자·이메일·IP·원시 연주 데이터는 넣지 않는다. 파일명은 `one-measure-backup-YYYY-MM-DD.json`이다.

가져오기 순서:

1. 사용자가 파일 선택. 최대 1MiB, MIME/확장자는 참고이고 실제 JSON 파싱·스키마 검증 실시.
2. 허용 키만 읽는다. `__proto__`, HTML, 스크립트, URL 실행 지시는 무시하거나 거부한다.
3. 최대 작품 20개, 이벤트·문자열·중첩 깊이 제한 검증.
4. 지원 가능한 이전 schemaVersion은 순수 migration 함수로 복사 변환. 미래 버전은 원본 유지 후 거부.
5. 추가될 작품 수와 충돌을 미리 보여 준다. 기본은 새 ID로 사본 추가이며 기존 것을 덮어쓰지 않는다.
6. 사용자가 선택한 교체만 원자적으로 수행하고 이전 내용을 복구 snapshot에 유지한다.
7. 성공 결과를 재조회한 뒤 파일에서 복원했다고 표시한다.

제목은 최대 40자, plain text로 렌더링한다. 가져오기 파일의 URL로 네트워크 요청하거나 외부 음원을 받지 않는다.

### 18.4 오프라인

서비스 워커로 앱 shell·해시된 JS/CSS·UI SVG·6개 퍼즐·기본 글꼴 또는 시스템 대체 경로를 캐시한다. 음색은 로컬 합성이므로 스트리밍 음원 의존이 없다. 서비스 워커는 secure context가 필요하며 배포는 HTTPS를 사용한다. [W3C Service Workers](https://www.w3.org/TR/service-workers/#secure-context)의 보안 요구를 따른다.

최초 방문이 오프라인이고 아직 캐시가 없으면 실행할 수 없다. “한번 접속해 준비를 마친 뒤 오프라인으로 사용할 수 있어요”라고 정확히 안내한다. 부분 다운로드를 완료로 표시하지 않는다. 캐시 manifest의 필수 자산을 모두 확인한 뒤에만 “오프라인 준비됨”을 보여 준다.

앱 버전별 cache name을 사용하고 새 버전 설치가 끝나도 플레이 중인 문서를 강제로 reload하지 않는다. 홈에서 “새 버전 적용”을 선택하면 저장 검증 → 오디오 정지 → 업데이트 → 재로드 순으로 처리한다. 이전 호환 캐시는 새 버전 성공 확인 후 제거한다. cache와 IndexedDB를 혼동하여 앱 업데이트 시 작품을 지우지 않는다.

브라우저가 저장 공간을 회수할 수 있다. 영구 보존을 약속하지 않고 내보내기를 안내한다. 저장 지속성 요청은 기능 지원 여부와 사용자 선택을 확인하여 구현하며, 거절되더라도 앱을 막지 않는다. [StorageManager.persist 설명](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)은 구현 참고로만 쓰고 지원을 실기기에서 확인한다.

### 18.5 개인정보와 안전한 기본값

첫 출시는 계정·이름·이메일·생년월일·위치·마이크·카메라를 요청하지 않는다. 외부 광고·트래커·소셜 로그인·외부 분석 SDK를 넣지 않는다. 진행과 작품은 기기에만 저장한다. 단, 웹사이트 접속 자체의 호스팅 접근 로그가 존재할 수 있으므로 운영자는 실제 호스팅의 로그 정책을 확인하고 개인정보 안내에 정확히 반영해야 한다. “서버에 어떤 정보도 남지 않는다”는 문구를 검증 없이 쓰지 않는다.

음악 파일이나 입력 기록을 제3자 AI 서비스로 보내지 않는다. 접근성·품질 진단에 필요하면 사용자가 선택한 최소 데이터만 로컬 파일로 내보낸다. 원격 오류 수집·연구 분석은 별도 동의·보존 기간·삭제 경로·수집 목적이 정의되기 전까지 비활성이다.

이 문서는 법률 자문이나 특정 관할 적법성 판정이 아니다. 아동 대상 출시·학교 배포·계정 도입 시 적용 규정과 동의·보호자 절차를 책임자가 별도로 검토한다. 범용 게임이라는 이유로 아동 관련 의무가 자동으로 없어지는 것으로 가정하지 않는다.

## 19 시각 디자인과 에셋 제작 명세

### 19.1 시각 방향

작은 공방의 작업대처럼 조각의 길이가 명료하게 보이는 2D 디자인을 사용한다. 장식은 학습 영역 밖에 두고, 선반·목재 무늬·도구가 음표나 쉼표를 가리지 않게 한다. 나이가 확정되지 않았으므로 유아 캐릭터를 기본 전제로 두지 않는다. 첫 버전은 캐릭터 없이도 완결되어야 한다.

색 예시는 배경 `#F7F5EF`, 본문 `#20262D`, 소리 조각 `#246B73`, 쉼 조각 `#715D8E`, 선택 강조 `#B35E22`를 출발점으로 한다. 이 값들만으로 대비 통과를 선언하지 않는다. 실제 배경·글자·상태 조합별 대비를 측정하여 일반 텍스트 4.5:1, 큰 텍스트 및 의미 있는 UI 경계는 적용 기준을 확인한다. 대비가 부족하면 색을 조정한다.

음표·쉼표 표준 기호는 직접 그린 벡터 또는 사용 권리가 확인된 음악 글꼴로 렌더링한다. 시스템 Unicode 음악 문자에만 의존하면 기기마다 누락·비율 차이가 생길 수 있으므로 최종 악보기호는 검증된 SVG로 고정할 수 있다. 기호 자체와 클릭 영역을 분리한다.

### 19.2 디자인 토큰

- 본문 기본 16px, 줄간격 1.5. 핵심 주문 18~20px. 실제 rem과 사용자 글자 크기를 존중한다.
- 간격: 4/8/12/16/24/32px 체계.
- 일반 버튼 최소 높이 44px, 주요 하단 버튼 48~56px.
- 카드 모서리 12px, 음표 조각 8px. 그림자보다 경계·모양으로 분리.
- 선택 테두리 3px와 선택 아이콘. 오류는 색+아이콘+설명.
- 배치 애니메이션 120~180ms, 성공 강조 250ms 이내. reduced-motion에서는 위치 변화 없이 상태만 즉시 갱신.
- 박 cursor는 이동 막대 또는 점 하나. 큰 화면 플래시를 박자에 맞춰 깜빡이지 않는다.

악기 한 종류라는 범위는 학습자의 조립 음색 하나를 뜻한다. 메트로놈 클릭과 알림 UI 소리는 기능적 보조이며 별도 곡·악기를 추가하는 콘텐츠로 취급하지 않는다. 성공 효과음은 선택이며 메트로놈과 겹치지 않게 한다.

### 19.4 제작 및 라이선스 절차

1. 기호·아이콘·배경 목록을 먼저 확정한다.
2. 직접 제작물은 작성자·원본·수정 권리를 기록한다.
3. 외부 글꼴/라이브러리/음원은 라이선스 원문·버전·출처·배포 조건을 목록화한다.
4. 기존 음악게임의 스크린샷·음원 추출·캐릭터 변형본은 사용하지 않는다.
5. AI 이미지 도구를 쓰더라도 음표 기호의 정확한 모양은 벡터 검수로 교체하고, 특정 게임의 화면·스타일 복제를 요구하지 않는다.
6. 앱의 저작권/라이선스 화면에 필요한 고지문을 넣고 릴리스 파일과 함께 보관한다.

## 20 성능과 호환성 예산

모든 수치는 제안된 출시 예산이다. 이 설계서 작성 단계에서 실제 앱 성능을 측정하지 않았다. 목표 기기는 착수 때 보유 실기기를 명시하고, OS·브라우저·출력 장치·전원 상태·측정 방법을 결과에 기록한다.

### 20.1 초기 예산

| 항목 | 초기 목표 | 측정 방법 |
| --- | --- | --- |
| 최초 핵심 다운로드 | 압축 전송 기준 500KB 이하 | production build와 Network 로그 |
| 전체 오프라인 필수 자산 | 2MiB 이하 | cache manifest 합계 |
| 첫 조립 가능 시간 | 정의한 중급 모바일/네트워크에서 p75 3초 이하 | 최소 20회 cold load, 중앙값·p75 |
| 편집 반응 | pointer→시각 반응 p95 100ms 이하 | 실기기 trace·event timing |
| 화면 이동 | p95 200ms 이하 | 로컬 전환 측정 |
| 저장 transaction | p95 100ms 이하, 실패 경로 별도 | 작은 실제 데이터 반복 |
| 도메인 판정 | 8이벤트 기준 5ms 이하 | 고정 fixture 1000회 bench |

| 재생 중 메인스레드 | 반복되는 50ms 이상 long task 제거 목표 | performance trace |

다운로드 예산에 음악 글꼴 전체나 불필요한 차트·애니메이션 라이브러리를 넣어 예산을 넘기지 않는다. 시스템 한글 글꼴을 우선 사용하고, 음악기호는 작은 SVG 모음으로 처리한다. 네트워크를 통한 글꼴 로딩 실패가 조립 기능을 막으면 안 된다.

### 20.2 오디오 성능을 정확하게 보고하는 방법

OfflineAudioContext 검사는 예약된 합성 신호의 위치·길이·무음을 확인할 수 있지만 실제 스피커·무선 연결·터치 지연을 증명하지 않는다. 실제 end-to-end 지연을 주장하려면 물리적 입력/출력 측정이나 동기화된 외부 기록이 필요하다. 단순 자동 브라우저 테스트로 “지연 10ms” 같은 광고 수치를 만들지 않는다.

MVP 출시에서는 절대 지연을 보증하는 대신 같은 기기에서 보정 후 재현성, 이벤트 누락 없음, 중단 시 무효 처리, 음악적 시간 간격의 일관성을 확인한다. 무선 출력의 변동이 크면 정밀 점수를 숨기고 조립·듣기·연습 모드로 안내한다.

### 20.3 기기 시험 행렬

- iOS Safari: 출시 시 지원 대상으로 선언할 현재·이전 주요 OS의 실제 iPhone 각 1대 이상
- iPad Safari: 터치+키보드, 세로/가로
- Android Chrome: 중급 기기와 저사양 기기 각 1대 이상
- Desktop Chrome·Edge·Firefox·Safari: 지원 가능한 조합에서 키보드·스크린리더·오디오 fallback
- 오디오: 내장 스피커, 유선 이어폰, Bluetooth 이어폰
- 네트워크: 정상, 느림, 최초 로드 실패, 캐시 후 오프라인, 업데이트 도중 끊김
- 접근성: VoiceOver/Safari, TalkBack/Chrome, 키보드만 사용, 200% 확대, reduced motion

Playwright의 WebKit 실행을 실제 iPhone Safari 시험으로 대신했다고 쓰지 않는다. 지원 목록은 테스트한 버전과 날짜로 별도 릴리스 문서에 고정한다. 지원하지 않는 브라우저에서는 데이터 손상 없이 읽기·내보내기 또는 간단한 안내를 제공한다.

## 21 단계별 개발 계획

아래 순서는 완료 기준을 통과해야 다음 단계로 넘어가는 단계형 계획이다. 한 명의 숙련 프런트엔드 개발자, 파트타임 음악교육 검수자·디자이너·QA를 가정한 초기 추정은 약 25~40 작업일이다. 기존 코드·인력·기기 가용성이 확인되지 않아 확정 일정이나 비용 약속이 아니다. 모든 일정을 단순 병렬 합계로 계산하지 않는다.

### P0 범위와 검수 기준 확정

입력: 본 설계서, 실제 목표 사용자·기기·운영 환경의 선택. 1~2일 제안.

작업:
1. MVP/후속 목록을 이슈로 분리하고 범위 변경 승인자를 정한다.
2. 6개 문제와 전이 문항을 음악교육 검수자가 읽는다.
3. 화면 폭 320/390/768/1280에서 정보 구조를 종이 또는 저충실도 UI로 확인한다.
4. 입력 맞춤값을 성적 보정이 아닌 연습 편의로 제시하는 문구를 확정한다.

산출물: 합의한 acceptance checklist, 문제 JSON 초안, 지원 기기 목록. 종료 조건: 음악적 중대 모순 0개, 범위 담당자와 검수 담당자가 미확정 항목을 승인 또는 보류로 분류.

### P1 음악 도메인 엔진

예상 2~3일. UI를 만들기 전에 time/meter/rhythm 모듈을 작성한다.

작업: 정수 tick·기약분수, 범위·겹침·빈칸 검사, canonical signature, note onset, rest spans, 재료 수, 붙임줄 예약 필드 거부, tempo 변환. UI 없이 25장의 fixture를 실행한다.

산출물: 순수 함수와 단위 테스트. 종료 조건: 알려진 정답·반례 전부 통과, property test에서 배치→undo 원상 복구, 3/4·6/8 시간 모델 계산 정확. 첫 출시 UI에 3/4·6/8을 노출하지는 않는다.

### P2 콘텐츠와 정답 검증기

예상 2~3일. 문제 JSON의 스키마, 제한된 rule AST, 오류 코드 우선순위를 만든다.

작업: L1~L6 데이터 작성, 잠금 불변 비교, 재고 검사, L4·L5 전수 열거, 참조 리듬 해시, 한국어 문장 연결. 잘못된 콘텐츠를 빌드에서 실패시킨다.

종료 조건: 예상 semantic 해답 수 `[1,1,1,3,2,1]` 확인, 대표 오답 각각 올바른 코드 반환, 모델 정답과 실제 검증기의 불일치 0개. L2의 initialEvents에 원래 N2가 남아 있어도 편집 가능 부분은 교체할 수 있어야 한다.

### P3 접근 가능한 조립 편집기

예상 3~4일. 탭 선택·배치와 목록형 편집부터 만든다. 드래그는 마지막에 얹는다.

작업: grid·팔레트·조각 선택·이동·삭제·분할·undo/redo·잠금 표시·길이 요약, 44px 대체 컨트롤, keyboard focus. 편집 commands와 reducer를 연결한다.

종료 조건: 마우스/터치 탭/키보드만으로 L1~L6 조립 가능, 320px 폭에서 기능 잘림 없음, 빈칸과 쉼표의 시각·의미 구별, 잘못된 드롭 후 원본 유지.

### P4 오디오 수직 시제품

예상 2~3일. 먼저 L3 한 마디만 정확히 들리는 최소 버전을 만든다.

작업: context 시작·중지·한 음색, 이벤트 예약, metronome bus, 4박 카운트인, 출력 커서, stop cleanup, 숨김 중단. `N4`와 `N2 N2`, `N2`와 `N1 R1`을 A/B로 확인한다.

종료 조건: OfflineAudioContext 기대 구간 일치, 실제 2종 모바일에서 소리 재시작·정지·쉼 구간 확인, 연타해도 중복 재생 없음. 지연 수치 미측정이면 정밀도 문구를 주장하지 않는다.

### P5 전체 문제 흐름과 설명

예상 2~3일. HOME→BUILD→FEEDBACK→다음의 흐름을 만든다.

작업: 튜토리얼 5단계, 6개 주문, 힌트 사다리, 다중 정답 도장, A/B, 독립/힌트/해답보기 기록, 소리 없는 대체 경로.

종료 조건: 각 문제의 실패→피드백→수정→통과 E2E, 도움을 본 사용자도 진행 가능, 탭 없이 모든 이론 문제 완료, false positive/negative 0개.

### P6 직접 치기와 입력 맞춤

예상 3~4일. 음악적 정답이 안정된 다음 운동 수행 기능을 붙인다.

작업: timestamp 수집, 시계 mapper, 보정 median/MAD, 동적 계획 매칭, miss/extra, fallback, 중단 무효화, 입력 연타·포커스·키 반복 처리.

종료 조건: 보정 부호의 고정 fixture 통과, 허용 창 경계 테스트, target0 처리, L4의 3개 모든 답에서 올바른 목표 생성, 이론 결과와 독립. 실기기에서 무선 출력이 불안정하면 practiceOnly 처리 확인.

### P7 저장과 복구

예상 2~3일. 진행 기록뿐 아니라 미완성 작품 복구를 구현한다.

작업: IndexedDB 원자 쓰기, debounce/checkpoint, previousGood, revision 충돌, export/import, 용량·권한 실패, 20슬롯 제한, 데이터 초기화 확인.

종료 조건: 새로고침·강제 종료 후 마지막 완료 저장 복구, 손상 current에서 previousGood 선택 가능, 가져오기 실패 때 기존 데이터 무변경, 다중 탭 충돌 보존.

### P8 오프라인과 업데이트

예상 1~2일. 핵심이 온라인에서 안정된 뒤 서비스 워커를 추가한다.

작업: 자산 manifest, 필수 캐시 검증, 최초 오프라인 안내, 버전 업데이트·old cache cleanup, IndexedDB migration와 cache version 분리.

종료 조건: 첫 온라인 준비 후 비행기 모드에서 6개 문제·자유모드·저장 동작, 업데이트 중 실패 후 이전 버전 사용, 플레이 중 강제 reload 없음.

### P9 디자인과 접근성 마무리

예상 2~3일. 기능 완성 후 에셋·전환 효과를 일관되게 적용한다.

작업: 기호 검수, 3종 의미 패턴, dark/high-contrast, 200% 확대, focus visible, 스크린리더 레이블, reduced motion, 라이선스 목록.

종료 조건: 실제 assistive technology로 전체 조립 경로 수행, 핵심 오류 severity-high 0개, 장식 제거해도 과제 의미 유지. 자동 접근성 검사만으로 완료 선언하지 않는다.

### P10 통합 QA와 사용성 파일럿

예상 3~5일. 22장 시험 행렬과 26장 평가 문항을 사용한다.

작업: 모바일 실기기, 오디오 interruption, 낮은 메모리, slow network, 저장 실패, 20분 soak, 신규 입문자 관찰, 음악교육 검수. 개인정보를 모으지 않는 내부 관찰부터 시작한다.

종료 조건: P0/P1 결함 0개, 주요 경로 P2 결함은 해결 또는 위험 승인, 모든 학습 문항의 정답·오답 이유 검수, 사용성 중대 장애 해결. 교육효과는 이 단계의 소규모 관찰로 확정하지 않는다.

### P11 출시 준비와 관찰

예상 1~3일. 실제 배포는 별도의 실행 승인과 호스팅 선택을 거친다.

작업: production build, HTTPS·cache headers, 보안 정책, source map 처리, 버전·지원 브라우저·개인정보·라이선스 화면, 롤백 절차, 릴리스 체크리스트.

종료 조건: 새 기기 clean session에서 6문제 완료, offline 준비, export→import 복원, 업데이트→rollback 데이터 유지. 출시 후 버그 수집은 사용자가 자발적으로 제공한 재현 정보부터 시작한다.

### 22.4 회귀와 릴리스 자동화

커밋마다 typecheck·lint·도메인 단위·콘텐츠 스키마·정답 열거를 실행한다. PR마다 상태 통합·DOM 접근성·핵심 E2E를 실행한다. 릴리스 후보마다 실제 모바일·오디오 출력·복구·오프라인 시험을 수행한다.

작업 완료란 코드만 작성한 상태가 아니다. 변경한 규칙에 적어도 하나의 정상·하나의 반례 fixture를 추가하고, 관련 문구·도움말·접근성 레이블·migration 영향까지 확인해야 한다. 정답 판정 변경은 `gradingVersion`, 콘텐츠 의미 변경은 `puzzleVersion`, 저장 구조 변경은 `schemaVersion`을 올린다.

테스트 실패를 고치기 위해 실제 기대 정답을 근거 없이 바꾸지 않는다. 음악 규칙이 틀린 경우 검수자의 설명과 변경 이유를 기록한다. 화면 스냅샷 업데이트만으로 음가·소리·판정의 일치가 증명되지 않는다.

### 23.3 제품 지표

첫 버전은 원격 분석 없이 로컬 집계로도 사용할 수 있게 한다. 연구 또는 제품 분석을 추가할 때 수집 여부를 별도 결정한다.

유용한 후보 지표는 첫 조각 배치 성공, L3에서 빈칸을 쉼으로 오해한 빈도, L4에서 두 번째 정답 발견, L6에서 onset 동일/duration 상이 오답 비율, 힌트 사용 경로, 전이 문항별 정답률, 저장 실패율이다. 평균 플레이 시간·연속 방문·높은 탭 점수만을 학습 성공으로 정의하지 않는다.

데이터를 수집한다면 이벤트 이름 예시는 `puzzle_objective_passed`, `hint_opened`, `concept_error_observed`, `save_failed`다. 불필요한 원시 timestamp·개인 제목·고유 기기 fingerprint를 첨부하지 않는다. 연구용 집계에서도 작은 집단 재식별 위험과 동의 범위를 검토한다.

## 24 후속 확장 상세 규칙

### 24.1 3/4와 6/8 비교 모듈

둘 다 8분음표 여섯 개 분량이지만 일반적인 큰 박의 묶음은 다르다. 3/4는 `2+2+2`의 세 큰 박, 6/8은 `3+3`의 두 큰 박으로 가르친다. 매우 느린 6/8에서 여섯 분할을 세는 등 실제 음악의 유연성은 후속 설명에 남기고, 입문 화면에서 “6/8은 무조건 여섯 큰 박”이라고 쓰지 않는다. 일반적인 분류 근거는 [musictheory.net의 Simple and Compound Meter](https://www.musictheory.net/lessons/15)다.

첫 비교에서는 8분음표의 초 길이를 250ms로 고정한다. 따라서 3/4는 4분음표=120, 6/8은 점4분음표=80으로 표시한다. 둘 다 1.5초짜리 마디여서 길이를 바꾸지 않고 묶음만 비교할 수 있다. 이후 큰 박 BPM을 같게 맞추는 비교에서는 마디 길이가 달라짐을 별도로 보여 준다.

| 요소 | 3/4 | 6/8 |
| --- | --- | --- |
| 내부 길이 | 1440tick | 1440tick |
| groupUnits | [1,1,1] with denominator4 | [3,3] with denominator8 |
| 시각 8분 묶음 | [2,2,2] | [3,3] |
| 큰 박 위치 u | 0,2,4 | 0,3 |
| 기본 세기말 | 하나-앤 둘-앤 셋-앤 | 하나-둘-셋 둘-둘-셋 또는 1-la-li 2-la-li |
| 음량 강조 예시 | 첫 큰 박 가장 강함, 다음 두 박 약함 | 첫 큰 박 강함, 둘째 큰 박 상대적 강조 |

강세는 항상 해당 위치의 실제 음이 크게 연주되어야 한다는 음악 법칙이 아니다. 이 앱의 metronome·시각 묶음이 박 구조를 설명하기 위한 교수 장치다. syncopation·hemiola·악센트 이동으로 실제 음의 강약은 달라질 수 있다.

확장 문제 E1: 3/4에 N2 세 개를 배치. 답 `N2 N2 N2`, 큰 박 3개.

확장 문제 E2: 6/8에서 점4분음표 두 개 배치. 답 `N3 N3`, 큰 박 2개. 점4분음표는 3u=720tick으로 팔레트와 schema를 확장한다.

확장 문제 E3: 8분음표 여섯 개를 양쪽에 놓고 큰 박 묶음을 선택. 3/4=[2,2,2], 6/8=[3,3]. 리듬 onset 배열은 같지만 박자 구조가 다름을 설명한다.

확장 문제 E4: 같은 길이의 두 마디를 듣고 강조/묶음 힌트를 고른다. 실제 음악에서는 단일 패턴만으로 박자를 유일하게 판단할 수 없는 경우가 있음을 추가 설명한다. 이 교수용 모델은 강세가 의도적으로 분명한 예시임을 밝힌다.

### 24.2 점음표와 붙임줄

점음표는 원래 길이의 1/2을 추가한다. 점4분음표는 3u, 점2분음표는 6u다. 6/8에서 점4분음표가 한 큰 박으로 쓰일 수 있으며 4/4에서는 1.5박이다. “점음표는 언제나 한 박 반”이라는 일반화는 금지한다.

붙임줄 편집을 추가할 때 다음 불변 조건을 적용한다.

- 연결은 시간적으로 인접한 note끼리만, pitch가 같아야 함.
- rest를 건너뛰거나 서로 다른 음높이를 연결할 수 없음.
- cycle·dangling ID·겹침·역방향 chain 금지.
- chain 길이는 각 durationTick 합, onset은 첫 note 한 개.
- tie 제거 시 재발음 생성. 재생 전에 변화 설명.
- 마디 경계를 넘는 chain은 multi-measure 모델이 들어온 이후에만 허용.
- 화면 fragment·원본 음표·sounding event를 각각 구분하여 undo 가능하게 함.

확장 문제 E5: `N2 N2`와 `N2~N2`를 비교. 총 길이 같음, 시작 횟수2 대1.

확장 문제 E6: 첫 박 뒤 반 박에서 시작해 다음 박 앞 반 박까지 이어지는 소리를 두 N1의 tie로 표현. 시작점1u, 길이2u, 발음1회. 두 N1을 다시 친 답과 구분한다.

### 24.3 다른 프로젝트와 연계하는 경우

사용자가 별도 프로젝트인 리듬마을·밤실공방 등과 연결하기를 원할 때만 선택적으로 연계한다. 이 앱은 해당 프로젝트 없이 독립적으로 시작·학습·저장·완료할 수 있어야 한다. 이름·세계관·로그인·폴더를 자동 통합하지 않는다.

연계가 승인되면 공통 데이터는 `meter`, `tempo`, `events`, `learningObjectiveIds` 정도의 중립적 리듬 interchange로 제한한다. 외부 앱이 보낸 점수나 정답 여부를 그대로 신뢰하지 않고 로컬 schema·음악 규칙을 다시 검증한다. 사용자의 작품을 다른 서비스에 자동 공유하지 않는다.

### 25.2 순수 검증 의사코드

```text
validateRhythm(document, puzzle):
  validate schema, rational duration, supported values
  for each event:
    if event.startTick < 0 or event.endTick > barLength: return E_OVERFLOW
  ordered = sort(events by startTick, then id)
  cursor = 0
  gaps = []
  for each event:
    if event.startTick < cursor: return E_OVERLAP
    if event.startTick > cursor: gaps += [cursor, event.startTick)
    cursor = event.endTick
  if cursor < barLength: gaps += [cursor, barLength)
  verify locked source events are unchanged
  if gaps not empty: return E_GAP with exact spans
  evaluate allowed constraints in deterministic priority order
  return objectivePass and semantic summary
```

실제로는 overflow·overlap·lock 등 여러 오류가 동시에 존재할 수 있다. UI에 보여 주는 대표 오류의 우선순위는 12장과 일치시킨다. 스키마에 실패하면 이후 연산은 수행하지 않는다. 도메인 테스트는 representative code뿐 아니라 모든 진단 목록도 확인할 수 있다.

### 25.3 속성 기반 테스트 아이디어

- 어떤 유효 문서든 이벤트를 배열상 섞어도 semantic signature가 같아야 한다.
- ID만 바꿔도 판정 결과가 같아야 한다.
- 인접한 쉼표를 나누거나 합쳐도 full semantic rhythm이 같다. 단 재료 개수 제한 문제에서는 inventory 조건이 별도로 실패할 수 있다.
- note를 둘로 나누면 총 길이는 같고 onset은 하나 늘어난다. 후속 tie split은 onset이 늘어나면 안 된다.
- 음표를 같은 길이 쉼표로 바꾸면 fullCoverage는 그대로이고 sounding duration과 onset 개수만 바뀐다.
- 템포를 바꾸면 tick·정답·순서가 바뀌지 않고 초 시간만 역비례로 변한다.
- 재생 snapshot을 만든 뒤 원본을 편집해도 실행 중 schedule은 바뀌지 않는다.
- serialize→parse→validate→serialize는 의미를 보존한다.
- migration은 입력 원본을 mutate하지 않으며 성공 전 current를 교체하지 않는다.
- 목표와 입력에 동일한 ms 상수를 더해도 탭 판정은 같다.
- 보정 offset과 rawError에 같은 상수를 더해도 correctedError는 같다.

## 26 전이 평가 문항과 파일럿 진행안

### 26.1 사전 문항 T1부터 T4

**T1 길이 합** 4/4에서 2분음표 하나와 4분음표 두 개가 한 마디를 채우는가? 정답: 예, 2+1+1=4박. “음표가 셋이므로 부족”을 선택하면 LO1 혼동으로 기록한다.

**T2 분할** 4/4에서 4분음표 하나와 같은 총 길이를 가진 것은 8분음표 몇 개인가? 정답: 2개. 기호 색·길이 막대 없이 표준 기호와 이름만 사용한다.

**T3 쉼** `N2 R2 N2 N2`에서 소리가 나지 않는 구간은 몇 번째 박인가? 정답: 두 번째 박. 총 길이는 4박이라는 후속 설명을 제공하되 문항 응답 전에는 제시하지 않는다.

**T4 시작과 길이** `N4`와 `N2 N2`의 비교. 정답: 총 길이는 같고 시작 횟수는 1회와 2회. 틀린 선택지: 총 길이도 같고 시작 횟수도 같다 / 두 번째가 항상 두 배 빠른 BPM이다. 선택 후 왜 그런지 한 문장으로 설명하게 하여 부분 이해를 확인한다.

### 26.2 사후 문항 T5부터 T8

**T5 새 길이 합** 4/4에서 4분음표 하나, 8분음표 둘, 2분쉼표 하나가 한 마디를 채우는가? 정답: 예, 1+0.5+0.5+2=4박. 표현 순서를 사전과 다르게 한다.

**T6 같은 시작 다른 지속** A=`N2 N2 N2 N2`, B=`N1 R1 N2 N2 N2`. 정답: onset은 둘 다 `[0,2,4,6]`u지만 B의 첫 소리는 반 박만 지속되고 첫 박 뒤쪽은 쉰다. “시작 시점이 같으니 완전히 같은 리듬”을 오답으로 분류한다.

**T7 조건 창작** “4분음표 두 개, 8분음표 두 개, 4분쉼표 하나로 4/4 한 마디를 만들어 보세요. 마디는 소리로 시작해요.” 총 길이 2+1+1=4박. 예시 답 `N2 N1 N1 R2 N2`; 다른 재료·길이·첫소리 조건을 충족한 순서도 인정한다. 화면 조립을 외운 정도를 줄이기 위해 흑백 기호 또는 종이에서 수행한다.

**T8 오류 설명** 누군가 “쉬는 박은 아무것도 안 놓으면 되므로 4분음표 세 개만 넣어도 완성된 4/4다”라고 말했다. 정답: 실제 음악에서 침묵도 시간이지만, 이 편집기의 완성 악보에는 남은 한 박의 쉼을 명시해야 한다. 빈칸은 미정이고 쉼표는 결정된 침묵이라는 설명을 인정한다. 앱 편집 규칙을 모든 음악 창작의 보편 법칙처럼 일반화하지 않는다.

### 26.3 채점 루브릭

선택 문항 T1/T2/T3/T5는 정오답과 선택한 오개념을 기록한다. 설명 문항 T4/T6/T8은 0=핵심 오해, 1=부분 설명, 2=길이·시작·쉼을 정확히 구분으로 제안한다. 창작 T7은 길이1점·재료1점·시작 종류1점·설명1점으로 분리한다. 탭 정확도를 이 점수에 넣지 않는다.

사전·사후 문항이 완전히 동일 난이도라고 검증된 것은 아니다. 총점을 직접 비교하기보다 목표별 변화를 먼저 본다. 교사 간 채점 일치도를 확인하려면 같은 익명 답안 일부를 두 검수자가 독립적으로 평가하고 의견 차이를 조정한다.

### 26.4 탐색적 사용성 세션

1. 참여자가 어떤 음악 경험이 있는지 선택적으로 확인한다. 불필요한 상세 개인정보는 기록하지 않는다.
2. 도움 없이 소리 켜기/무음 시작, 첫 조각 놓기, L1 수행을 관찰한다.
3. L3에서 빈칸과 쉼표를 어떻게 이해하는지 질문한다.
4. L4에서 “같은 길이”와 “시작 횟수”의 차이를 자신의 말로 설명하게 한다.
5. L6에서 듣기·기호 대체 경로를 선택하게 하고 실제 사용 경로를 기록한다.
6. 새 과제 T5~T8에서 격자·색 도움을 줄인다.
7. 결과 화면을 보고 무엇을 잘했고 무엇이 어려웠다고 생각하는지 질문한다.
8. 저장·재방문·내보내기를 수행한다.

관찰자가 정답을 유도한 경우 독립 수행으로 기록하지 않는다. 중단·읽기 어려움·소리 환경 문제를 학습 능력 부족으로 분류하지 않는다. 녹음·촬영은 기본하지 않고 필요하면 대상·목적·보존 기간을 설명한 별도 동의를 받는다.

## 27 개발 착수 결정과 출처 및 검증 범위

### 27.1 착수 때 확인할 질문

이 설계로 도메인·콘텐츠·UI 시제품을 시작할 수 있다. 다만 실제 개발 계약·출시 전에 다음 네 가지를 확정한다.

1. 주 학습자 연령과 음악 경험, 소리 사용이 가능한 환경

### 27.3 이 문서에서 완료한 검증과 남은 검증

문서 차원의 자동 검사 59개를 수행하여 통과했다. 검사 범위는 6개 문제의 길이·onset·정답 집합과 개수, JSON 구문과 필수 참조, 템포·시간 단위, 보정 부호, onset만 같은 duration 반례, 27개 장과 코드 블록 구조 등이다. 별도 독립 검토에서도 음악 수치와 다중 정답 수를 확인하고, 입력 수집창·팔레트 예외·쉼표 병합·저장 충돌·문항 표현의 모순을 수정했다. 이는 설계 문서의 일관성 확인이며 실제 앱의 테스트 결과는 아니다.

실제 앱은 아직 구현하지 않았으므로 브라우저 실행·화면 렌더·터치·스크린리더·실기기 오디오·학습효과·네트워크·저장 회복력을 검증했다고 주장하지 않는다. 이 문서의 체크리스트는 그런 검증을 빠뜨리지 않고 구현하도록 만든 개발 계약이다.

첫 개발 목표는 L3 한 문제에서 “조립 → 올바른 쉼을 포함한 재생 → 구체 피드백 → 저장 후 복원”이 모바일에서 끝까지 작동하는 수직 시제품이다. 이를 통과한 다음 6개 문제와 선택적 직접 치기를 확장한다. 화려한 보상 화면보다 음악의 의미·편집 안전성·오디오 신뢰성을 먼저 완성한다.
